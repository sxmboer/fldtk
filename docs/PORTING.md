# Porting status

fldtk (`fl.*`) is a native D reimplementation of FLTK, not a binding layer.
This document lists, module by module, which part of FLTK each fldtk
module covers, what state it is in, and what it leaves out.

Source links point at FLTK's GitHub mirror
(`https://github.com/fltk/fltk/blob/master/...`). FLTK 1.5.0 (its
`fltk_version.dat`) is the reference.

## Status legend

- **Complete** — works, no known gaps.
- **Partial** — usable, with the missing pieces named in the row.
- **Deferred** — not ported yet, for the reason given in the row.
- **Not applicable** — nothing to port: C/C++ language scaffolding
  (macros, export annotations), or FLTK's XForms compatibility layer
  (see `CONVENTIONS.md`'s "Out of scope" section).
- **Not started** — no D module yet.

The general rules for how FLTK's C++ maps onto D (delegates for
callbacks, `string` for text, and so on) are in `CONVENTIONS.md` and are
not repeated per module.

**Unicode**: FLTK's UTF-8 layer (`FL/fl_utf8.h`) is not ported. D source
is Unicode at the language level (`string` is UTF-8, `dchar` is a code
point, and Phobos's `std.utf`/`std.uni` cover decoding, encoding and case
mapping), Fluid writes `.fl` files and generated `.d` files as UTF-8, and
code generated by Fluid handles Unicode with no extra library calls.

**What counts as API to port**: members FLTK marks deprecated, keeps out
of its manual (`\internal`, `\cond`, `#ifndef FL_DOXYGEN`), or leaves
without a doc comment of their own are not ported and not listed below.
The rows name only documented members fldtk leaves out, and why.

**Maintaining this file**: it describes the current state. When a module
changes, rewrite its row to match; history belongs in commit messages.

## Core / support

### `FL/Enumerations.H`

**Status:** Complete — `fl.enumerations`
([header](https://github.com/fltk/fltk/blob/master/FL/Enumerations.H))

`Align`/`Boxtype`/`Color`/`Font`/`Fontsize`/`Labeltype`/`When`/
`CallbackReason`/`Event`/`Damage`, key names (`Keysym`), mouse button
numbers, `Fl::event_state()` bits, `Cursor`, `Fl_Arrow_Type`/
`Fl_Orientation`, `ContrastMode`/`ContrastFunction`, and `colorTable` (the
256-entry default color table from `src/fl_cmap.h`).

- `FL_BUTTON(n)` is the function `stateButton(int n)`.
- `Fl_Contrast_Function` is a delegate, `ContrastFunction`.

### `FL/Fl.H`

**Status:** Complete — `fl.core`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl.H),
[src/Fl.cxx](https://github.com/fltk/fltk/blob/master/src/Fl.cxx))

The event loop (`run()`/`wait()`/`wait(double)`/`check()`/`flush()`),
timers, idle and check callbacks, `add_fd()`, thread locking
(`lock()`/`unlock()`/`awake()`), schemes (`scheme()`/`is_scheme()`/
`reload_scheme()`), the color table (`get_color()`/`set_color()`), font
registration and enumeration, the clipboard (text and images), drag and
drop (`Fl::dnd()`), multi-monitor geometry, input methods,
`Fl::modal()`/`Fl::grab()`, `add_handler()`/`add_system_handler()`/
`event_dispatch()`, command-line parsing (`Fl::args()`) and
`Fl::visual()`. Callbacks are delegates throughout.

**Scaling.** Each screen has its own scale (`screenScale(int)`/
`screenScale(int, float)`; `screenScalingSupported()` is 2 on Linux and
Windows). Drawing code reads the scale of the window being drawn
(`fl.core.currentScale()`), set whenever a window becomes current. Mouse
coordinates are divided by the scale of the window the event came from.

- The scale is the base scale (the desktop's: `Xft.dpi` on X11, each
  monitor's DPI on Windows, 1 on Wayland, whose compositor applies its
  scale itself) times a zoom.
- Ctrl +/- step the zoom through 50, 67, 80, 90, 100, 110, 120, 133, 150,
  170, 200, 240 and 300%, Ctrl-Shift +/- by 1% within that range, and
  Ctrl-0 sets it back to 100% (`keyboardScreenScaling()`); a popup shows
  the new value.
- A program starts with `fl.core.startupZoom()`, the `Zoom` startup
  setting: the `FLDTK_SCALING_FACTOR` environment variable if set,
  otherwise the user's value, otherwise the system's (`startupSetting()`,
  `~/.config/fldtk/options.prefs`, `%APPDATA%\fldtk\options.prefs` on
  Windows). Ctrl +/-/0 store the user's value (`persistZoom()`), so every
  fldtk program starts with the zoom last chosen; `fldtk-options` shows
  and changes it.
- With the `FLDTK_FLUSH_OUTPUT` environment variable set, a program's
  `stdout` is line buffered (on Windows unbuffered) from before `main()`
  (`fl.output_buffering`), so its output through a pipe shows line by
  line; Fluid's File > Run sets it.
- On X11 a desktop scale change while windows are open is followed:
  `RRScreenChangeNotify` re-reads the monitors, and a change of
  `_NET_WORKAREA` or `RESOURCE_MANAGER` re-reads `Xft.dpi` and rescales
  every window; the new desktop scale becomes Ctrl-0's reference. Window
  sizes are read from the server (`XGetWindowAttributes()`), since a
  ConfigureNotify's size can be wrong. Under GNOME's XWayland scaling,
  which resizes X11 windows itself, `fl.platform_x11` records each
  window's size at the RandR notification and asks for it again once the
  compositor has settled (see the comment above `recordedSizes_`).
- `screenNum(x,y)`/`screenNum(x,y,w,h)` compare a point in FLTK units
  with each screen's scaled bounds; `screenNumUnscaled(x,y)` compares a
  device-pixel point (from `getMouse()`) with the unscaled bounds.

**`fatal()`** calls the handler set with `setAbort(AbortHandler)`. The
default handler prints the message to stderr and throws
`fl.core.FatalError`, so a program can catch it; a program that wants to
exit instead sets its own handler.

- The clipboard's `paste()` asks for the selection with
  `XConvertSelection()` and decodes image data from memory.
- `clipboardContains()` waits for the selection owner's answer in a
  blocking loop that discards other events.
- `option()`'s system and user preference files are read, never written.
- Boxtypes and label types are drawn through tables: `fl.draw`'s
  boxtype table (drawing function, insets, flags and focus drawing per
  boxtype) and `fl.widget`'s label type tables (16 slots). `setBoxtype()`
  (both overloads), `getBoxtype()` and `setLabeltype()` read and write
  them with delegates (`BoxDrawFunc`, `BoxDrawFocusFunc`,
  `LabelDrawFunc`, `LabelMeasureFunc`), so a program can replace a
  built-in type or add one in a `freeBoxtype`/`freeLabeltype` slot.
- Also: `abiCheck()`, `programShouldQuit()`, `system()` (returns the
  command's exit code), `display()`, `idle()`, `ready()`,
  `removeNextTimeout()`/`timeoutList()`, `selectionToClipboard()`,
  `selectionOwner()`/`selection()`, `useHighResGL()` (stored; it only
  matters on macOS) and `drawGlTextWithTextures()` (see `FL/gl.h`).
- Not ported:
  - `Fl::atclose`/`set_atclose()`/`default_atclose()`, kept by FLTK for
    backward compatibility; set the window's callback instead.
  - `Fl::gl_visual()` and `Fl::own_colormap()`: one TrueColor visual is
    used for non-GL windows, and there is no colormap support.
  - `Fl::box_color()`/`set_box_color()`: boxtypes are drawn in the color
    they are given.
  - `Fl::screen_driver()`/`system_driver()`: there are no driver objects.
  - `Fl::thread_message()` (deprecated); use `awake()`.
  - `Fl::set_labeltype(Fl_Labeltype, Fl_Labeltype)`, declared but never
    defined in FLTK.

### `FL/core/events.H`

**Status:** Complete — `fl.core`
([header](https://github.com/fltk/fltk/blob/master/FL/core/events.H))

Event state (`e_number`/`e_state`/`e_x`/`e_y`/... and their accessors),
`focus()`/`belowmouse()`/`pushed()`, `test_shortcut()`,
`handle(Event, Widget)`, `dispatch()` (FLTK's `Fl::handle()`, through
`event_dispatch()`), `grab()`, `get_mouse()`/`get_key()`, and
`add_handler()`/`add_system_handler()`.

- `Event.zoomEvent` is sent after every rescale. `FL_APP_ACTIVATE`/
  `_DEACTIVATE` are sent on X11 under an EWMH window manager (from
  `_NET_ACTIVE_WINDOW`). `FL_SCREEN_CONFIGURATION_CHANGED` is never sent.
- **Touch and gestures** (`fl.touch`, with `fl.win32_touch`, `fl.xinput2`
  and the Wayland and X11 backends; sample `examples/touch_test.d`):
  `Event.zoomGesture`, `Event.rotateGesture`, `Event.swipeGesture`, and
  raw touch (`Event.touchDown`/`touchMove`/`touchUp`/`touchCancel`) for
  widgets subscribed with `Touch.subscribe()`, with `eventZoom()`,
  `eventRotation()`, `eventFingers()` and `eventGesturePhase()`.
  `zoomGesture` also sets `eventDy()` to (zoom - 1) x 1000. Gestures go
  where the mouse wheel goes.
  - On a touchscreen one finger acts as the mouse (its press waits up to
    100 ms for a second finger, so a pinch starting on a button doesn't
    click it), and two fingers make zoom, rotate and scroll events:
    worked out in `fl.touch` from the raw contacts on Wayland (`wl_touch`)
    and X11 (XInput 2.2), and by Windows itself (`WM_GESTURE`, with
    single-finger pan turned off).
  - Touchpad pinch, turn and swipe come from Wayland's pointer-gestures
    and X11's XInput 2.4 (X.Org server 21.1 and later); Windows sends a
    touchpad pinch as Ctrl + mouse wheel.
  - Tested on touchscreens with `examples/touch_test.d`: tapping,
    two-finger scrolling, pinch, turn and raw multi-touch on Windows
    (six fingers, raw touch making no mouse events), and raw multi-touch
    on Wayland. X11 touch and touchpad gestures are untested on
    hardware.

### `FL/core/options.H`

**Status:** Complete — `fl.core`
([header](https://github.com/fltk/fltk/blob/master/FL/core/options.H))

`Fl_Option`/`option()`, read from the system-wide and per-user
preferences (`fl.preferences`, `fldtk`/`options`) on first use.
`optionKey()` and `optionDefault()` give each option's preferences key
and default. The same preferences group holds the startup settings
`Backend`, `Graphics`, `Scheme` and `Zoom`, which `startupSetting()`
reads after their environment variables (`FLDTK_BACKEND`,
`FLDTK_GRAPHICS`, `FLDTK_SCHEME`, `FLDTK_SCALING_FACTOR`).
`simpleZoomShortcut` is deprecated and has no effect: Ctrl and '=' always
zoom in. `visibleFocus()`/`dndTextOps()` are shortcuts for two
options. The `fldtk-options` program (`source/options/`) writes the
preferences; it shows the startup settings and only the options fldtk
acts on, so the GTK, Zenity
and Kdialog file chooser options and the GTK print dialog option, which
fldtk has no use for, aren't in it. The setter reads the
preferences first, so an option set at the top of `main()` is not
overwritten by the first read later.

### `FL/core/function_types.H`

**Status:** Not applicable — n/a
([header](https://github.com/fltk/fltk/blob/master/FL/core/function_types.H))

C function-pointer typedefs. Each subsystem that takes a callback

### `FL/core/pen_events.H`

**Status:** Partial — `fl.pen` (the API, with
`src/drivers/Base/Fl_Base_Pen_Driver.*`), `fl.wayland_pen_driver`,
`fl.win32_pen_driver`; samples `test/penpal.d` and `examples/pen_test.d`
([header](https://github.com/fltk/fltk/blob/master/FL/core/pen_events.H))

Pen and tablet input: pressure, tilt, twist, barrel pressure, the eraser,
barrel buttons, hovering, and several pens told apart. Widgets subscribe
with `Pen.subscribe()`; see `fl.pen`'s module comment for the event flow.
The pen events are members of `Event` (`Event.penTouch`, ...), the API is
class `Pen`'s static members, and destroying a subscribed widget
unsubscribes it.

- Drivers for Wayland (`zwp_tablet_v2`) and Windows (`WM_POINTER*`,
  Windows 8 and later, its functions looked up in user32.dll at run
  time). On X11 a pen acts as a mouse; an X11 driver through XInput2 is
  planned (`CONVENTIONS.md`).
- `fl.pen` dispatches for both drivers: the widget under the pen is found
  by walking the window's widget tree, a widget destroyed while handling
  a pen event ends the dispatch, and losing the pointer capture
  mid-stroke keeps the barrel buttons' state.
- On Wayland the pen works fldtk's own title bar like the mouse
  (`fl.platform_wayland.penOnFrame()`). A tool reporting its distance
  from the surface gets `Pen.Trait.proximity`.
- Not ported: the tablet's pad (buttons, rings, strips) and a tool's
  wheel.
- Tested with a Lenovo Yoga's pen on Windows: pressure, tilt, hover,
  the eraser, barrel buttons, traits, a subscribed subwindow, an
  unsubscribed widget getting the pen as a mouse, no pen events under a
  modal dialog, drawing at the exact pen point at any scale, and
  `penpal`'s Tests menu. Twist is untested (that pen doesn't report it).
  The Wayland driver is untested on hardware.

### `FL/Fl_Widget_Tracker.H`

**Status:** Complete — `fl.widget_tracker`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Widget_Tracker.H))

Tells whether a widget was destroyed during a callback, for code that
fires more than one callback in a row. The state lives in a registry in
`fl.core` (`watchWidgetPointer()`/`releaseWidgetPointer()`/
`clearWidgetPointer()`), not in the widget: `destroy()` resets an
object's memory to `.init` after its destructor, which would wipe a flag
kept in the widget. `WidgetTracker` is a stack-only `struct` that can't
be copied.

### `FL/Fl_Device.H`

**Status:** Complete — `fl.image_surface`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Device.H))

`SurfaceDevice` (`Fl_Surface_Device`): a `pushCurrent()`/`popCurrent()`
stack plus `surface()`/`isCurrent()`. Below it:
`fl.widget_surface.WidgetSurface` (base of `ImageSurface`, `CopySurface`,
`SvgFileSurface`, `EpsFileSurface`, `PdfFileSurface` and
`fl.paged_device.PagedDevice`, which `PostscriptFileDevice` and the
printers extend; see `FL/Fl_Widget_Surface.H`), and
`fl.gl_display_device.GlDisplayDevice`, which sends `fl.draw`'s
primitives to `fl.gl_graphics_driver.GlGraphicsDriver`.

- A surface's platform code sits in the surface class itself, behind
  the protected hooks `doSetCurrent()`/`doEndCurrent()`; there are no
  per-platform driver classes.
- The display has no object of its own: `surface() is null` means the
  display.
- `Fl_Device_Plugin` is not needed: GL is always linked, so
  `fl.core.captureWindow()` and `WidgetSurface.draw()` call
  `GlWindow.capture()` directly for the GL windows they meet.

### `FL/Fl_Graphics_Driver.H`

**Status:** Complete — `fl.graphics_driver`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Graphics_Driver.H))

The abstract `GraphicsDriver` covers rectangles, lines, colors, polygons,
line style, clipping, arcs and pies, vertex paths, plain and rotated
text, and images and bitmaps. Drivers: `SvgGraphicsDriver`,
`PostscriptGraphicsDriver`, `GlGraphicsDriver`, the Cairo driver, and on
Windows `GdiGraphicsDriver` and its subclass `GdiPlusGraphicsDriver`
(which also draw on screen there).

- On X11 without Cairo, `fl.draw` draws through Xlib and Xft itself:
  `currentDriver is null` means that path, non-null means "send to this
  driver".
- Text measurement (`width()`/`height()`/`descent()`/`text_extents()`)
  and `fl_font()` always use the display's fonts, whatever the driver.
- Images go through two driver calls, `drawImage()` and `drawBitmap()`
  (plus `drawImageScaled()` on resolution-independent surfaces); FLTK's
  per-image-class `draw_rgb()`/`draw_pixmap()`/`draw_bitmap()`/
  `draw_image()` are not ported.

### `FL/fl_draw.H`

**Status:** Complete — `fl.draw`
([header](https://github.com/fltk/fltk/blob/master/FL/fl_draw.H))

Lines, rectangles, polygons and their outlined and filled forms; every
boxtype family (the built-in ones, rounded, oval/round/diamond, and the
gtk+, plastic, gleam and oxy schemes); text through Xft (`fl.xft`) or, in
Cairo mode, Pango, with word wrap, shortcut underlines, `@` symbols,
right-to-left glyph order and rotated text (`fl_draw(int angle, ...)`);
text measurement; color math (`fl_color_average()`/`fl_inactive()`/
`fl_contrast()`, with the CIELAB-based default and the FLTK 1.3
algorithm, switchable through `contrastMode`/`contrastLevel`/
`contrastFunction`); clipping; the transform stack and vertex paths
(`fl_begin_*()`/`fl_vertex()`/`fl_curve()`/complex polygons); arrows;
drawing and reading images (`fl_draw_image()`, `fl_read_image()`,
`fl_capture_window()`); offscreen buffers; and overlay rectangles.

- Text: a trailing `\n` doesn't start another line (`splitTextLines()`,
  shared by both `fl_draw()` overloads and `fl_measure()`).
- Fonts: unrotated Xft text opens fonts by name (`XftFontOpenName()`);
  rotated text builds an `FcPattern` with an `FC_MATRIX` rotation
  (`fl.xft`'s `xftFontForAngled()`), cached per face, size and angle.
  There is no X core-font fallback. The 12 classic faces plus symbol,
  screen, screen bold and Zapf Dingbats resolve to a family; Helvetica,
  Courier and Times map to the Fontconfig aliases "sans", "mono" and
  "serif" (see `getFont()`'s doc comment for why the alias matters).
  `smoke-tests/text_baseline.d` and
  `smoke-tests/browser_height_probe_fltk.cxx` check vertical metrics.
- Clipping is a stack of rectangles.
- Visuals: TrueColor/DirectColor only, no colormaps.
- Images (`fl_draw_image()`/`fl_draw_image_mono()`, buffer and callback
  forms) honor negative deltas: a negative `l` flips vertically, a
  negative `d` horizontally, and sizes and the gray/color test come from
  `|d|`. A 2- or 4-byte-per-pixel buffer is alpha-blended
  (`alphaBlendImage()`). `test/unittest_images` exercises the flips.
- **Scaling** (`fl.core.currentScale()`, see `FL/Fl.H`) applies to every
  drawing call; at scale 1 nothing changes.
  - Rectangles, lines, polygons and `fl_scroll()` round through
    `scaledFloor()`. `fl_xyline()`/`fl_yxline()` draw filled rectangles
    as thick as the scaled line (or the width a `lineStyle()` set), so
    adjacent lines leave no gaps.
  - The default line is 1 pixel wide below 200% and `int(scale)`
    pixels from 200% up, as in FLTK, and a line style's width is
    multiplied by the scale; every line primitive (`fl_line()`,
    `fl_rect()`, `loop()`, polygon outlines, line strips, `fl_arc()`)
    draws with it. The style is applied again when the scale changes
    (`penScaleChanged()`). An explicitly wide `fl_xyline()`/`fl_yxline()`
    is centered on its logical row's device pixels.
  - Fonts open at `size * currentScale()` device pixels; measurements
    and the pen position are converted back to FLTK units.
  - Vertex paths scale every point in one place
    (`appendVertexPoint()`); a driver that asks for unscaled points
    (`GraphicsDriver.wantsUnscaledVertices()`, e.g. the GL driver) gets
    them as given.
  - Arcs, pies, circles, check marks and clipping scale too.
  - Offscreens: `createOffscreen(w, h)` takes FLTK units and makes the
    buffer at the current scale, `beginOffscreen()` draws into it at that
    scale, `copyOffscreen()` takes FLTK units, and `rescaleOffscreen()`
    remakes a buffer at a new scale with its picture scaled.
    `fl.image_surface` and double buffering use device-pixel buffers
    (`createOffscreenPixels()`, the seven-argument `copyOffscreen()`).
  - Images drawn at the scale are resampled with
    `Image.scalingAlgorithm()`, bilinear by default: `RGBImage.draw()`
    through `copy()`, raw buffers (`fl_draw_image()`, mono and callback
    forms) through `resampleImage()`, on X11 and on screen on Windows.
    The Cairo driver smooths a stretched image only when it is bilinear,
    and a GDI page stretches with `HALFTONE`.
  - 1-bit bitmaps are resampled to the current scale (`Bitmap.copy(w,
    h)`), and `drawBitmapFixed()` scales the destination and crop offsets.
  - A Pixmap's transparency mask is placed at the same scaled position
    as its image. A surface's translation (`pushTranslate()`, one per
    nested window drawn) is kept in FLTK units and scaled once, so a
    high-resolution `ImageSurface` draws a window and its subwindows at
    any scale (`test/gl_capture.d`).
  - `releaseDrawable()`, called before a window is destroyed, forgets
    the window's `XftDraw` and the last-drawn drawable that
    `createOffscreen()` uses as a reference.
- Also: `fl_shortcut_label()` (in `fl.core`; the name stays, since
  `Widget.shortcutLabel()` exists), `drawPixmap()`/`measurePixmap()`,
  `overrideScale()`/`restoreScale()`, `canDoAlphaBlending()` (always
  true), `fl_frame(string, x, y, w, h)`/`frame2()`, and `drawBoxFocus()`
  (uses the boxtype's own focus function when it has one).
- `circle()` and the vertex-path `fl_arc(double, ...)` use as many chords
  as keep each within 1/8 device pixel of the curve (`arcSegments()`,
  the rule of FLTK's `fl_arc.cxx`), at the current scale and through the
  current matrix. The count comes from the larger semi-axis of a
  stretched circle, since evenly spaced points stray furthest at an
  ellipse's flat sides. They reach every driver as points.
- `fl_arc(int, ...)` and `fl_rect()` draw a wide line centered on the
  box's edge, so half of it falls outside. `fl_pie()` and `fl_rectf()` are
  fills and ignore the line style: on X11 and GDI the pie's edge is drawn
  with the default line (`build/arc_width` shows all four at several
  widths).
- `fl_expand_text()` is not ported: `fl_measure(text, w, h)` with `w` set
  to the wrap width gives the size of wrapped text, and `fl_draw(text, x,
  y, w, h, alignWrap)` draws it. For a layout of your own, use
  `std.string.lineSplitter()`, `std.algorithm.splitter(' ')`,
  `fl.draw.width()` and `std.ascii.isControl()`.
- Not ported: `fl_clip_region()` (clipping has no regions) and
  `fl_set_status()` (the input method has no status area).
- Printing and SVG export don't depend on the display scale: on Windows
  the printer driver draws at a fixed scale of 1 and SVG export differs
  only by a pixel of rounding here and there; on Linux PostScript and SVG
  from `test/device` at 150% match the window.

## Platform / windowing headers

The platform code is three concrete modules, `fl.platform_x11`,
`fl.platform_wayland` and `fl.platform_win32`, with no driver class
hierarchy. On Linux, X11 or Wayland is chosen at run time, and
`fl.window`/`fl.core` reach the active one through `fl.platform`, a set
of free functions that forward to it. Windows code sits in
`version (Windows)` branches next to the Linux ones.

### `FL/platform.H`

**Status:** Not applicable — n/a
([header](https://github.com/fltk/fltk/blob/master/FL/platform.H))

FLTK's public access to native handles (`Fl_X`, `fl_xid()`/`fl_find()`,
`fl_open_display()`, the platform headers). fldtk has no public native
handles, so that programs stay portable: the equivalents are
`package(fl)` (`fl.window.Window.xid()`, `fl.platform.openDisplay()`).
`fl.platform.backend()` is public and tells which Linux display server a
program runs on (`test/fltk_versions` shows it). A public accessor is
added only for a need that has no portable alternative.

### `FL/x.H` + `FL/x11.H` + `src/drivers/X11/*` + `src/drivers/Xlib/*` (rect/color/font parts)

**Status:** Partial — `fl.platform_x11` + `fl.xlib` + `fl.xft`
([FL/x.H](https://github.com/fltk/fltk/blob/master/FL/x.H),
[FL/x11.H](https://github.com/fltk/fltk/blob/master/FL/x11.H),
[src/Fl_x.cxx](https://github.com/fltk/fltk/blob/master/src/Fl_x.cxx))

Window creation and destruction, subwindows included; a `select()` event
loop over the X connection, timers, `addFd()` entries and idle callbacks;
mouse, keyboard, focus and crossing events (autorepeat, double and triple
clicks, NumLock keypad mapping, and every mouse button number: side
buttons are 4 and 5, then 10, 11, ...); cursors; repainting clipped to
the damaged rectangle; window manager hints (size range, fullscreen,
maximize, iconify through EWMH, icons through `_NET_WM_ICON`,
`WM_CLASS`, `_NET_WM_PID`); the clipboard and selection (text and
images, with change notification through Xfixes or polling, and large
transfers in parts through `INCR`); XDND drag and drop within and between
programs, with the dragged text shown at the pointer, and a dropped
picture (`image/png`, else `image/bmp`) arriving as an image paste ahead
of any text the source also offers, and dropped files (`text/uri-list`)
arriving as one path per line (`fl.core.uriListToPaths()`); XIM input with the preedit at the
cursor; and multi-monitor geometry.

- `fl.xlib`, `fl.xft`, `fl.fontconfig`, `fl.xcursor`, `fl.xfixes`,
  `fl.xinerama`, `fl.xrandr`, `fl.xshape` and `fl.xinput2` are
  `extern(C)` bindings for the system libraries of the same names.
- A new top-level window is kept on screen: it is clamped to the monitor
  it overlaps most, or the first monitor, so a position saved under
  another monitor layout can't open it out of sight.
- Cursors: every top-level window gets the arrow cursor when created
  (a rootless Xwayland server would otherwise show none). The diagonal
  resize cursors come from the cursor theme (`nwse-resize`/`size_fdiag`/
  `bd_double_arrow` and their mirror images), or are drawn from SVG at
  the theme's cursor size.
- Popup windows (`Widget.Flag.menuWindow`) are override-redirect.
- `Fl::visual()` packs pixels for the selected visual's channel masks
  (`figureOutVisual()`); the shared GC is made once, for the default
  visual's depth.
- `enableIm()`/`disableIm()` do nothing on X11.
- Per-monitor DPI (`fl.core.screenDpi()`): each Xinerama monitor is
  matched to its RandR 1.5 monitor (`XRRGetMonitors()`) and gets its own
  DPI; without RandR 1.5, or when a monitor reports 0 mm, the X screen's
  pixels over millimeters are used. The startup scale comes from
  `Xft.dpi`, not from this. `smoke-tests/screen_dpi.d` prints both.
- When a window's centre moves onto a screen with another scale, the
  rescale follows a second later through a timeout, during which only
  position changes are applied, and an open popup menu is closed.
  `smoke-tests/screen_scale_live.d` checks it on a second monitor.
- `flushDamage()` turns a damaged rectangle into device pixels by
  rounding its corners outward, clamped to the offscreen buffer, so no
  stale sliver is left at fractional scales.
- Typed text without an input method is encoded from the keysym through
  `fl.keysym_ucs` (FLTK's `XKeysymToUcs()` tables).
- Under a window manager without EWMH (`_NET_SUPPORTING_WM_CHECK`),
  maximizing resizes the window to the work area
  (`Window.maximizeByResize()`), and fullscreen shows the window again as
  an override-redirect window covering its screens that grabs the
  keyboard. A window shown with `fullscreen()` already called asks for
  `_NET_WM_STATE_FULLSCREEN` and `_NET_WM_FULLSCREEN_MONITORS` before it
  is mapped.
- The native-handle functions of `FL/x11.H` (`fl_x11_xid()`,
  `fl_x11_find()`, `fl_x11_gc()`, `fl_x11_glcontext()`,
  `fl_x11_use_display()`, `Fl_XFont_On_Demand`) are not ported (see
  `FL/platform.H`). The X-only functions outside `fl.platform` (the
  `Display*`, visual, colormap, X resources, `-display`) are used by
  X11-only code such as GLX.

Missing:
- Dragging out carries text only; `COMPOUND_TEXT` and other charset
  targets are not negotiated. A dropped `INCR` transfer has not been
  tried yet.
- The sideways wheel's direction (buttons 6/7) has been tried with a
  thumb wheel, a TrackPoint, a touchpad and a touch screen, not with a
  tilting scroll wheel (`build/value_wheel` shows it).
- `readPixelsFromDrawable()` reads only 16, 24 and 32 bpp layouts.
- A CJK input method (ibus, fcitx) has not been tried; dead keys through
  XIM work (`smoke-tests/ime.d`).
- Damage is one bounding rectangle per flush, so a little more than
  needed may be repainted.
- Not ported: `XWMHints.icon_pixmap` icons (`_NET_WM_ICON` is used).

### `FL/wayland.H`

**Status:** Complete — `fl.platform_wayland` and `fl.wayland_decoration`,
with bindings `fl.wayland_client`, `fl.wayland_cursor`, `fl.xkbcommon` and
generated protocol modules; built with Cairo only
([header](https://github.com/fltk/fltk/blob/master/FL/wayland.H))

Ported from FLTK's `src/drivers/Wayland/` at FLTK commit `3a049d826`.
FLTK's Wayland driver is under active development; to see what changed
since then:

    git -C ~/Repositories/fltk diff 3a049d826 -- src/drivers/Wayland src/drivers/Cairo

`fl.platform` uses this backend when `XDG_RUNTIME_DIR` is set and a
Wayland connection can be made. The `Backend` setting (`fldtk-options`)
picks one for every program, falling back to X11 when it asks for
Wayland and there is none; `FLDTK_BACKEND=x11` or `FLDTK_BACKEND=wayland`
forces one for a single run, and is an error when it can't be met. A unittest build uses X11 unless
`FLDTK_BACKEND` says otherwise, since the unit tests are written for X11.
Wayland draws only through `fl.cairo_graphics_driver`, so it needs
`FLDTK_HAVE_CAIRO`; the `linux-no-cairo` configuration builds X11 only.

- **Display and screens:** compositor, subcompositor, shm,
  `xdg_wm_base`, outputs, and the socket in `fl.core`'s event loop
  (libwayland's prepare/read calls, `dispatchEvents()`). Screen geometry
  in logical pixels from xdg-output (from the integer output scale when
  that is missing).
- **Windows:** `xdg_toplevel`s. A window with a border asks for
  server-side decorations (xdg-decoration), which KDE and the wlroots
  compositors draw. Where the compositor leaves them to the program
  (GNOME, Weston, no xdg-decoration), fldtk draws its own frame
  (`fl.wayland_decoration`): a subsurface below the window with a title
  bar in the program's colors (title in Pango; minimize, maximize and
  close buttons, only those the compositor supports through
  `xdg_toplevel.wm_capabilities`; a double click maximizes, the right
  button opens the compositor's window menu, dragging moves the window)
  and an invisible 8-pixel margin that resizes it, left out when
  maximized, tiled or not resizable, and no frame when fullscreen. The
  window geometry includes the title bar, so sizes from the compositor
  and the size range are adjusted by its height. The frame does not
  follow the desktop theme.
- Configure, resizing by the user and the program, close, minimize,
  maximize, fullscreen (`fullscreenActive()`/`maximizeActive()` follow the
  compositor's states; a fullscreen change the compositor makes sends
  `Event.fullscreen`), title, size range, modal and non-modal parents,
  xdg-dialog for dialogs, xdg-activation when a shown window is shown
  again, window icons through xdg-toplevel-icon where the compositor has
  it (not KDE Plasma 5.27 or GNOME; there the desktop shows the icon of
  the `.desktop` file matching the app id), and shaped windows. A window
  that moves itself while a mouse button is held is moved by the
  compositor (`xdg_toplevel.move`).
- Menus and tooltips are `xdg_popup`s placed where fldtk's menu engine
  puts them and updated where the compositor moves them; the Ctrl +/-
  indicator is a popup centred on the window. Subwindows are
  desynchronized `wl_subsurface`s clipped to their parents.
- **Drawing:** each window draws through `fl.cairo_graphics_driver` into
  its own Cairo image buffer, copied into a shared-memory `wl_buffer`
  (one pool per buffer) on commit and paced by frame callbacks; drawing
  outside a repaint is committed by the next flush. An overlay is drawn
  over a copy of the window's pixels. Offscreens and image surfaces are
  Cairo image surfaces, `fl_scroll()` moves pixels within the buffer,
  and `fl_overlay_rect()` works. Integer output scales become buffer
  scales; fractional scales are drawn at the exact scale
  (wp-fractional-scale and viewporter). `fl.cairo`'s context for a
  window is its buffer's. A window counts as exposed after its first
  configure.
- **OpenGL:** `fl.wayland_gl_window_driver` with bindings `fl.egl` and
  `fl.wayland_egl`: EGL configs and contexts, a `wl_egl_window` and EGL
  surface on each GL window's surface at the integer buffer scale, swaps
  paced by frame callbacks, the software overlay, and `gl_start()`
  through a transparent subsurface. See `FL/Fl_Gl_Window.H`.
- **Input:** pointer enter, leave, motion, buttons (side buttons 4 and
  5, then 10, 11, ..., as on X11) and wheel, with double clicks;
  keyboard through xkbcommon (modifiers, keypad with NumLock off, key
  repeat at the compositor's rate, dead keys and compose sequences as
  marked text); input methods through text-input-v3 (preedit as marked
  text, commits, the cursor position for the candidate window);
  `eventKey()`/`getKey()`; cursors through the cursor-shape protocol or
  the cursor theme named by `XCURSOR_THEME`/`XCURSOR_SIZE`, and cursors
  made from images. Ctrl +/- rescaling, starting from
  `fl.core.startupZoom()`.
- **Data exchange:** the clipboard (`wl_data_device`, text and PNG/BMP
  images) with change notification (`fl.core.addClipboardNotify()`), the
  middle-click selection (primary-selection protocol), and text drag and
  drop both ways, with the dragged text, black on white, as the drag
  icon. A dropped picture (PNG/BMP, the clipboard's choice) arrives as an
  image paste, ahead of any text the source also offers; dropped files
  (`text/uri-list`) arrive as one path per line
  (`fl.core.uriListToPaths()`).
- `fl_beep()` rings the desktop bell through xdg-system-bell where the
  compositor has it, and otherwise writes a BEL character to stderr.
- **Bindings:** `fl.wayland_client`, `fl.wayland_cursor` and
  `fl.xkbcommon` (keymap, state and compose only) are hand-written. The
  protocol modules (`fl.wayland_protocol`, `fl.xdg_shell_protocol`,
  `fl.tablet_protocol`, `fl.cursor_shape_protocol`,
  `fl.primary_selection_protocol`, `fl.text_input_protocol`,
  `fl.fractional_scale_protocol`, `fl.viewporter_protocol`,
  `fl.xdg_activation_protocol`, `fl.xdg_dialog_protocol`,
  `fl.xdg_toplevel_icon_protocol`, `fl.xdg_output_protocol`,
  `fl.xdg_decoration_protocol`, `fl.xdg_system_bell_protocol`) are
  generated by `source/devtools/wayland_scanner.d` and checked in; its
  header lists the commands. They hold the `wl_interface` tables and the
  request wrappers, so building fldtk needs neither wayland-scanner nor
  the protocol XML files. They were generated from wayland 1.24 and
  wayland-protocols 1.47.

What Wayland does not provide, which the rest of fldtk otherwise assumes:
- Global coordinates: a program can't place its windows or learn where
  they are. A toplevel's origin is (0, 0), so fldtk's "root" coordinates
  are the window's own; `fl.menu_popup` places menus in them.
  `fl.core.getMouse()` reports the last pointer position in a window, and
  `Window.hotspot()` and `screenXYWH()`-based placement have no effect on
  a toplevel. Saved window positions are ignored; no session-management
  protocol is in wayland-protocols yet.
- The work area: `screenWorkArea()` asks for a maximized window that is
  never shown and uses its size when there is one screen and the size is
  less than 50 pixels short of the screen's; the work area then starts at
  the screen's origin. With several screens, each screen's work area is
  the whole screen.
- Drawing on demand: there is no `Expose`; a surface is redrawn by
  attaching a new buffer, paced by frame callbacks.
- Fullscreen across several screens (`fullscreenScreens()`): a program
  can ask for fullscreen on one output only, so the window is fullscreen
  on its current screen. Spanning screens needs the X11 backend.

### `FL/win32.H`

**Status:** Partial — `fl.platform_win32` + `fl.gdi_graphics_driver` +
`fl.gdiplus_graphics_driver` + `fl.gdiplus`
([header](https://github.com/fltk/fltk/blob/master/FL/win32.H))

The Windows platform module. It uses druntime's `core.sys.windows.*`
bindings directly; functions newer than those bindings
(`SetProcessDpiAwarenessContext`, `GetDpiForMonitor`, the pointer and
gesture APIs) are looked up at run time.

**Windows and events.** Top-level `HWND`s and child `HWND`s for
subwindows (destroyed recursively, with no window manager negotiation);
a `MsgWaitForMultipleObjects()` message loop with the timer queue; mouse,
keyboard, paint, resize, close and focus messages dispatched through
`fl.core.dispatch()`.

- `fakeXWm()` computes border and title bar sizes
  (`AdjustWindowRectEx()`, or `GetSystemMetrics()` estimates) for window
  creation (style flags from `border()`, resizability and `modal()`),
  program-initiated resizes (`resizeWindow()`), and the size range during
  an interactive resize (`WM_GETMINMAXINFO`).
- Double clicks come from Windows (`CS_DBLCLKS`).
- A key press peeks for the `WM_CHAR`/`WM_SYSCHAR` that
  `TranslateMessage()` queued, so one `Event.keyDown` carries both
  `eventKey()` and `eventText()`. Punctuation keys are mapped for the
  active keyboard layout (`oemKeysym()`).
- Borderless top-level windows (tooltips, menus) are shown without
  activating them.

**Drawing.** `GdiPlusGraphicsDriver` (antialiased) draws on screen;
plain `GdiGraphicsDriver` is used if `GdiplusStartup()` fails.

- `GdiGraphicsDriver` implements the whole `GraphicsDriver`: colors
  (a 256-entry color table and a 16-brush cache), rectangles, lines,
  polygons, line style, clipping, arcs, pies, vertex paths, text and
  images. Coordinates are scaled by `fl.core.currentScale()` through
  `floorScaled()`, clipping and images included; vertex paths arrive
  already scaled from `fl.draw`.
- `GdiPlusGraphicsDriver` (on `fl.gdiplus`, a binding to GDI+'s flat C
  API) overrides `color()`, `line()`, `polygon()`,
  `arcUnscaled()`/`pieUnscaled()`, `lineStyle()` and the vertex-path
  `end*()` calls, and inherits the rest. `lineStyle()` honors
  `FL_CAP_SQUARE` and `FL_JOIN_BEVEL`. Closed loops are drawn as separate segments, so
  their corners are capped rather than joined.
- `lineStyle()` stays in effect when the color changes: every pen is
  made in the current style, and a cached pen is reused only in the
  style it was made in.
- `drawImage()` uses `StretchDIBits()`, and `AlphaBlend()` (msimg32) for
  2- and 4-byte pixels, falling back to blending over white. The DIB is
  built per call. `drawBitmap()` uses two masked `StretchBlt()` passes
  and honors the crop offsets `cx`/`cy`.
- Repaints call `InvalidateRect()` with the damaged rectangle.

**Fonts and text.** An `HFONT` cache per face, size and angle
(`CreateFontW()`/`GetTextMetricsW()`); the built-in faces map to
"Microsoft Sans Serif", "Courier New", "Times New Roman", "Symbol",
"Terminal" and "Wingdings". Widths are cached per code point; combining
marks have no advance (`fl.nonspacing`, generated from FLTK's
`spacing.h`; `smoke-tests/nonspacing_width.d`). `textExtents()` measures
the glyph ink (`GetGlyphIndicesW()`/`GetGlyphOutlineW()`, or
`GetCharacterPlacementW()` for surrogate pairs). Rotated text, and font
and size enumeration (`setFonts()`/`getFontSizes()` through
`EnumFontFamiliesW()`, synthesizing bold variants only from a regular
weight). Fonts open at the scaled size (`scaledFontSize()`) and every
metric is divided back by the scale. The layout of text (`fl_draw()`'s
alignment, wrapping, symbols and underlines) is shared code in
`fl.draw`.

**Cursors.** Every `Cursor` maps to a stock `IDC_*` cursor;
`WM_SETCURSOR` keeps the window's cursor (the arrow by default); RGBA
images become cursors (`image_to_icon()`). `Cursor.default_` is the
arrow.

**Monitors and DPI.** Monitors from `EnumDisplayMonitors()`/
`GetMonitorInfoW()`, with their work areas; `screenXYWH()`/
`screenWorkArea()`/`screenNum()`/`getMouse()` work in FLTK units. The
process is made per-monitor DPI aware, and each monitor's scale comes
from its own DPI (`GetDpiForMonitor()`), which is also the base scale
Ctrl-0 returns to.

- `WM_DPICHANGED` finds the new screen from the centre of the suggested
  rectangle and rescales only that window
  (`Window.resizeAfterScaleChange()`). `WM_SIZE` and `WM_MOVE` ignore the
  echo of the program's own resize (`resizeBugFix_`).
- The primary monitor is found with `MonitorFromPoint(0, 0)`.
- A window without a position opens at `CW_USEDEFAULT`.
- `smoke-tests/multi_monitor_scale.d` checks two windows on two monitors
  with different scales.

**Clipboard.** `copy()`/`paste()` through `OpenClipboard()`:
`CF_UNICODETEXT` for text, and images from `CF_DIB` (24/32 bpp
directly; palette-indexed or compressed DIBs through
`SetDIBitsToDevice()` onto an `ImageSurface`) or `CF_ENHMETAFILE`
(through `PlayEnhMetaFile()`). Windows has no primary selection, so
`copy(..., 0)`/`paste(..., 0)` stay within the program.
`addClipboardNotify()` uses the clipboard viewer chain
(`SetClipboardViewer()`, `WM_DRAWCLIPBOARD`, `WM_CHANGECBCHAIN`;
`test/clipboard.d`). `smoke-tests/clipboard_image_fallbacks.d` puts both
kinds of image on the clipboard itself.

**Window state.** Fullscreen (moved and sized over its monitors, without
frame; `fullscreenOff()` restores the old geometry), maximize, iconify,
tracking of maximize and restore done by the user (`WM_SIZE`), a window
iconified before its first `show()` opening iconic, and window icons
through `WM_SETICON` (the size closest to `SM_CXICON`/`SM_CXSMICON`). A
borderless window is maximized by resizing it to the work area
(`Window.maximizeByResize()`), so it doesn't cover the taskbar. Window
titles follow `label()`.

**`addFd()`.** Anonymous pipes can't be waited on, so registered
`fdRead` entries are polled with `PeekNamedPipe()` every 50 ms
(`pollFds()`; `examples/howto_add_fd_and_popen.d`).

**Drag and drop.** Through COM (`IDropTarget`/`IDropSource`/
`IDataObject`, `RegisterDragDrop()`/`DoDragDrop()`), with one drop target
for the process. A dropped picture arrives as an image paste
(`eventClipboardType() == clipboardImage`, an `RGBImage` in
`eventClipboard()`), ahead of any text the source also offers. The
formats are read from the source's `EnumFormatEtc()` list, best first:
"PNG" (global memory or a stream), `CF_DIB`, a browser's image file
(`FileGroupDescriptorW` + `FileContents`, a PNG/JPEG/GIF/BMP/SVG
decoded by its extension; not when real files are offered), then an
enhanced metafile (only when no text is offered, since Word offers one
for selected text too). Tested on Windows 11 with pictures from Word,
PowerPoint, Chrome and Edge, and image files from Explorer
(`smoke-tests/drop_image.d`); `smoke-tests/drop_formats.d` lists what a
source offers. Other
drops deliver text: `CF_UNICODETEXT`, `CF_TEXT` (through
`MultiByteToWideChar(CP_ACP, ...)`), or a file list from `CF_HDROP` as
`\n`-separated paths (`examples/howto_drag_and_drop.d`,
`smoke-tests/drop_image.d`). Dragging out is one blocking `DoDragDrop()`
call.

**Input methods.** Composed text (CJK, the emoji picker) arrives as a

### `FL/Fl_Image_Surface.H`

**Status:** Complete — `fl.image_surface.ImageSurface`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Image_Surface.H))

Draws into an offscreen buffer and returns the picture as an `RGBImage`

- `mask()`: one or more masks, applied when `image()` is called.
- `highRes` makes the buffer `fl.core.currentScale()` device pixels per

### `FL/Fl_Widget_Surface.H`

**Status:** Complete — `fl.widget_surface.WidgetSurface`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Widget_Surface.H))

The base of every surface that draws widgets: `draw(Widget)`/
`traverse()` (into subwindows too), `origin()`, `drawDecoratedWindow()`
(with the window's title bar), and `printWindowPart()`. `printableRect()`
fails in the base class; subclasses that know their page size override it.
Subclasses: `ImageSurface`, `CopySurface`, `SvgFileSurface`,
`EpsFileSurface`, `PdfFileSurface` and `fl.paged_device.PagedDevice`
(base of `PostscriptFileDevice`, which `fl.printer_posix.Printer`
extends; `fl.printer_win32.GdiPagedDevice` extends `PagedDevice` for the
Windows printer and PDF).

- `drawDecoratedWindow()` captures only the top of the frame on Linux
  (the title bar); left, right and bottom stay empty.
- `printWindowPart()` reads the window back through
  `fl.core.captureWindow()` (`XGetImage()` on X11, `BitBlt()` +
  `GetDIBits()` on Windows, the window's buffer on Wayland). A
  `DoubleWindow` is read from its offscreen buffer; a single-buffered
  window from the screen, where parts covered by other windows come back
  black.
- `captureWindow()` then captures each subwindow by itself and copies it
  over its part of the result, since an offscreen buffer holds no
  subwindows and GL draws into a surface of its own. A GL window is
  captured with `GlWindow.capture()`, which redraws it and reads the frame
  before it is swapped to the screen; `draw()` uses it to draw a shown
  `GlWindow` as an image. `test/gl_capture.d` checks `captureWindow()`,
  `ImageSurface.draw()` and printing for single- and double-buffered
  windows.
- `draw(Widget, int, int)` reads the origin from `xOffset_`/`yOffset_`:
  calling `origin(x, y)` with two `int` variables would resolve to the
  setter a subclass overrides and reset the origin.
  `PostscriptFileDevice.rotate()` does the same.

### `FL/Fl_Printer.H`

**Status:** Complete — `fl.printer.Printer`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Printer.H))

`fl.printer` picks `fl.printer_win32.Printer` on Windows and
`fl.printer_posix.Printer` elsewhere. `fl.printer_posix` compiles on
every platform, so `smoke-tests/printer_fltk_dialog.d` can show its
dialog on Windows too (without printers: it uses `lpstat`/`lp`/`lpr`).

**Linux.** `fl.printer_posix.Printer` extends `PostscriptFileDevice`.
`beginJob()` shows the print dialog (from FLTK's `print_panel`, with its
Properties panel for page size and output mode, and Collate), then
writes to a file or pipes the PostScript to `lp`/`lpr`
(`std.process.pipeShell()`).

- The color and grayscale pictures in the dialog are SVG.
- Collate is enabled when the job has more than one page and more than
  one copy is asked for (`PrintPanel.updateCollateState()`).
- Printer names are listed from `lpstat -p -d` or `/etc/printcap`, parsed
  by separately tested functions.
- Page size and output mode are kept per printer in the `fldtk/printers`
  preferences; a stored output mode out of range is ignored.
- There is no GTK print dialog; fldtk never loads GTK or Qt.

**Windows.** `fl.printer_win32.Printer` extends `GdiPagedDevice` and adds
the `PrintDlg()` dialog. `GdiPagedDevice` holds the page handling
(margins, `origin()`, `scale()`, `rotate()`, `translate()`, pages through
`StartDoc()`/`StartPage()`/`EndPage()`/`EndDoc()`) and draws into the
printer's `HDC` with its own `GdiGraphicsDriver`.

- The driver runs at a fixed scale of 1 (`useFixedScale(1.0)`): the
  printer's `MM_ANISOTROPIC` mapping already accounts for the page. It is
  `resolutionIndependent()`, so images print at their own resolution
  (`drawImageScaled()`).
- `pushClip()` maps the clip rectangle's four corners to device units
  (`LPtoDP()`) and builds a polygon region, since `SelectClipRgn()` takes
  device units and the page may be rotated.
- Where the printer can't `AlphaBlend()`, `drawImage()` falls back to a
  dithered mask. Bitmaps and pixmaps print with the on-screen
  `drawBitmap()`.
- `printableRect()` is computed in `beginPage()`/`scale()` and cached.
- `beginPage()` resets `fl.draw`'s clip stack, which all surfaces share.

### `FL/Fl_PDF_File_Surface.H`

**Status:** Complete — `fl.pdf_file_surface.PdfFileSurface`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_PDF_File_Surface.H))

Writes drawing to a PDF file, one page at a time, used like `Printer`.
`beginJob(defaultFileName)` shows a page-format dialog (page size, with
"Set as default" stored under `PDF/page_size` in the `fldtk/printers`
preferences, and orientation, remembered for the next call), then a
`NativeFileChooser`; `beginDocument(path, format, layout)` writes to a
given path. Both return 0, 1 (cancelled) or 2 (error, with a message).
One unit is one point; lines and text stay vectors, and images keep their
own resolution: `RGBImage` and `Pixmap` pass their own pixels to
`drawImageScaled()` (`Image.drawNative()`), an `SvgImage` is rasterized at
`SvgImage.documentPixelsPerUnit` (4, 288 dpi), and `Bitmap`s are passed
at their own size.

- **Linux:** a private `CairoGraphicsDriver` subclass draws onto a Cairo
  PDF surface (PDF 1.4) at scale 1. Margins, `scale()`, `origin()`,
  `rotate()` and `WidgetSurface` translations go into the page matrix
  (`pageMatrix()`). Text is laid out by Pango and scaled so each string
  has the width the display's fonts measure (`fl.draw.width()`), so a
  label fits where it fits on screen. Vertex paths arrive in whole
  points. A build without Cairo (`--no-cairo`) has the class, but
  `beginJob()`/`beginDocument()` return 2 with a message.
- **Windows:** extends `GdiPagedDevice` and prints with GDI to the
  "Microsoft Print to PDF" printer (Windows 10 and later), with the page
  size and orientation in a `DEVMODEW` and the output going to `path`
  (`StartDocW()`). Page formats with a Windows paper code (`DMPAPER_*`)
  are requested by that code, the others (A0, A1, A7-A9, B0-B3, B7-B10) as
  a custom size, which the PDF printer may not honor. Without that
  printer, `beginDocument()` returns 2 with a message. The module's
  unittest doesn't run on Windows (it would print).
- `scale()` moves the origin back to the top left of the printable area,
  so `origin()` is called after it.

`test/device.d`'s "PdfFileSurface" option prints the selected widget or
window to PDF; the unittest writes a two-page document.

### `FL/Fl_PostScript.H`

**Status:** Complete — `fl.postscript`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_PostScript.H))

`EpsFileSurface` (`Fl_EPS_File_Surface`) and `PostscriptFileDevice`
(`Fl_PostScript_File_Device`), writing PostScript level 2 directly in
every build. `PostscriptGraphicsDriver` implements `GraphicsDriver`:
vector text (Latin, Latin Extended-A and PostScript's standard extra
characters, as real glyphs), rotated text, RGB/RGBA/gray images and 1-bit
bitmaps (RLE + ASCII85). Images keep their own resolution
(`drawImageScaled()`).

- Text in a font from `freeFont` up, or containing any other code point
  (Greek, Cyrillic, CJK, Hebrew, ...), is drawn with the display driver
  into an `ImageSurface` at twice its size and written as a 1-bit mask in
  the text color (`drawExtra()`). Right-to-left text (`rtlDraw()`) takes
  the same paths after `fl.draw` reverses it
  (`smoke-tests/postscript_text.d`).

- Vertex paths arrive transformed from `fl.draw`. Each sub-loop of a
  complex polygon (`fl_gap()`) starts its own sub-path, so no edge joins
  them (`endComplexPolygonParts()`).
- RGBA and gray+alpha images are clipped to their pixels that aren't
  fully transparent (one `rectclip`), so a `Pixmap`'s transparent color
  shows what is behind it; partly transparent pixels are blended over the
  page background.
- A bitmap is drawn at its own size and clipped to the visible
  rectangle, as on screen.
- `closeCommand` is a `bool`.
- `draw(Widget)`/`drawDecoratedWindow()` print widgets showing RGBA
  images, pixmaps and bitmaps (`test/device`, PostScript output).

### `FL/Fl_SVG_File_Surface.H`

**Status:** Complete — `fl.svg_file_surface`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_SVG_File_Surface.H))

`SvgGraphicsDriver`/`SvgFileSurface` implement the whole `GraphicsDriver`:
rectangles, lines, colors, polygons, line style, clipping, arcs and pies
(a transformed unit circle), vertex paths (`endLoop()` is a closed

- Clip paths get increasing ids; nesting comes from `fl.draw`'s clip

### `FL/Fl_Cairo.H`

**Status:** Complete — `fl.cairo`, on `fl.cairo_c` + `fl.cairo_c_xlib` +
`fl.cairo_c_win32`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Cairo.H))

`CairoState` (`Fl_Cairo_State`), `src/Fl_Cairo.cxx`, and the
`Fl::cairo_*()` functions: `cairoMakeCurrent(Window)`, `cairoCc()`/
`cairoCc(cairo_t*, bool)`, `cairoFlush()` and `cairoAutolinkContext()`,
re-exported from `fl.core` and `fl`.

- Only in a Cairo build (`version (FLDTK_HAVE_CAIRO)`): the Linux
  default, left out with `linux-no-cairo`; on Windows the `windows-cairo`
  configuration, linking static Cairo/Pango libraries built with MSYS2's

- On Windows, `smoke-tests/cairo_steps.d` (the static libraries alone,
  printing each step first), `cairo_window_steps.d` (`CairoWindow`) and
  `pango.d` (text layout) check the build layer by layer; build them with

  emoji Pango shows depends on the installed fonts.
- `fl.cairo_c`/`fl.cairo_c_xlib`/`fl.cairo_c_win32` bind the whole public
  Cairo 1.18.4 API (`cairo.h`, `cairo-pdf.h`, `cairo-ps.h`,
  `cairo-svg.h`, `cairo-script.h`, `cairo-tee.h`, `cairo-xlib.h`,
  `cairo-win32.h`), transcribed from the C headers. Every struct's size
  and layout and every enum value were compared with a C compiler, and
  the function list against GtkD's `cairo.c.*`. Names follow GtkD's C

  also under its C name (`CAIRO_FORMAT_ARGB32`). They are written from

- On Windows, `fl.mingw_runtime` runs the GCC constructors of the static
  libraries (pixman, GLib, GObject), which the Microsoft-style C runtime
  never calls: its static constructor walks lld-link's `__CTOR_LIST__`
  (`-lldmingw`) in MinGW's order.
- `cairoMakeCurrent(Window)` keeps a context while the drawing target,
  size and screen scale stay the same, and hands it out each time in the
  state it was made in (scaled to the screen), so nothing carries over
  from an earlier draw; a new size or scale makes a new one.
- On X11 the context is a surface of its own on the window's drawable,
  also in Cairo display mode (`FLDTK_GRAPHICS=cairo`). `cairoMakeCurrent()`
  first sends the graphics driver's pending drawing to the X server, and
  `cairoFlush()` marks the drawable changed for the driver, so the two
  draw in program order. On Wayland the context is the one the window's
  buffer is drawn with.
- `cairoAutolinkContext(true)` (FLTK's FLTK_OPTION_CAIRO_EXT) gives every
  window except GL windows a context as it is drawn, and in
  `Window.makeCurrent()`, so `draw()` reads it with `cairoCc()`
  (`smoke-tests/cairo_autolink.d`, `USE_CAIRO_AUTOLINK` in
  `test/cairo_test.d`).
- The macOS branch is not ported (no macOS backend).

## Widget base, windows

### `FL/Fl_Widget.H`

**Status:** Complete — `fl.widget`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Widget.H))

Geometry, label, callbacks, flags, focus, active and visible state,
damage (with a damage rectangle bounded by the window), `&` shortcuts in

### `FL/Fl_Group.H`

**Status:** Complete — `fl.group`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Group.H))

The class is `FlGroup`, since `Group` would collide with Phobos's
`std.algorithm.iteration.Group` in code that imports both `fl` and `std`

`clipChildren()`, `current()`/`begin()`/`end()`, and `handle()`/

- `handle(Event.focus)` without a navigation key tries the saved focus
  and then the children in order, so `takeFocus()` on a group outside a

- `FlGroup`'s own code uses the non-virtual `rawArray()`/`rawChildren()`,

- `drawChild()`/`updateChild()` skip a child only when nothing it paints
  is in the clip: its box, and for a group that doesn't clip its

### `FL/Fl_Window.H`

**Status:** Complete — `fl.window`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Window.H),
[src/Fl_Window.cxx](https://github.com/fltk/fltk/blob/master/src/Fl_Window.cxx))

`show()`/`hide()`, size range, named and image cursors, fullscreen and
maximize (following changes made by the window manager, and on chosen
monitors), `modal()`/`nonModal()`, subwindows, `shape()`, iconify (also
before the first `show()`), icons, `decoratedW()`/`decoratedH()`, title
changes on a shown window, double buffering, and the window type flags
(`setMenuWindow()`, `setTooltipWindow()`, `setOverride()`, an
override-redirect window on X11). Also `clearModalStates()`,
`defaultCursor()`, `asDoubleWindow()`/`asOverlayWindow()`, `osId()` and
`allowExpandOutsideParent()` (Wayland only). The platform work is in
`fl.platform_x11`, `fl.platform_wayland` and `fl.platform_win32`.

- `~this()` hides a shown window (skipped in a GC finalizer).
- The default `WM_CLASS` is `"fldtk"`.
- A `nonModal()` window (modal or non-modal) gets `WM_TRANSIENT_FOR` on
  X11.
- `isOverride()` reads `setOverride()`'s flag (`override` is a D
  keyword).
- There is no virtual `flush()`; repainting is done by the platform
  module's `flushDamage()` (see `fl.double_window`).
- `forcePosition()` adds `USPosition` to the size hints; the Ctrl +/-
  indicator uses it to centre itself.
- `shape()`'s mask is made at the window's size in device pixels. A
  `Pixmap` shape is converted to an RGBA image and masked on its alpha.
- **Rescaling** (`resizeAfterScaleChange()`): the window keeps its
  device-pixel position, read from the last position the window system
  confirmed (`devicePosX_`/`devicePosY_`), and only its size changes, so
  repeated Ctrl +/- doesn't move it. Only a window whose centre would end
  up off its screen, and a fullscreen window, get a computed position.
  The exact position is passed only to the window being rescaled
  (`exactDeviceTarget_`), not to subwindows resized along with it.
  `isARescale_` makes `resize()` resize the native window even though its
  size in FLTK units is unchanged.

- `hotspot()` keeps the window inside the work area of the monitor the
  mouse is on, leaving room for the frame: estimated sizes on X11, the
  system metrics on Windows.

### `FL/Fl_Gl_Window.H`

**Status:** Complete — `fl.gl_window`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Gl_Window.H))

Contexts, `makeCurrent()`, buffer swaps, FLTK widgets drawn over a GL
scene (text included), the simulated overlay, GL1/GL3 shader-program
switching for `modeOpengl3`, and `gl_start()`/`gl_finish()` for drawing
GL into any window (`fl.gl`). A `GlWindow` works as a top-level window,
a subwindow, or inside a plain `Window`.

- X11 (GLX), Wayland (EGL) and Windows (WGL). Platform calls go through
  `fl.gl_window_driver`, which forwards to `fl.wayland_gl_window_driver`
  on Wayland; `GlWindow`, `fl.gl_graphics_driver`, `fl.gl_display_device`
  and `fl.gl` have no platform code.
- Text is drawn with textures, or with bitmap fonts in display lists
  (see `FL/gl.h`).
- `capture()` redraws the window and reads the frame before the swap
  (see `FL/Fl_Widget_Surface.H`).
- On Wayland every GL window is double-buffered and drawn at the
  integer buffer scale (the compositor resamples it at a fractional
  scale), and a GL subwindow isn't clipped to its parent.
  - Changing `mode()` of a shown window takes effect at the next
    `makeCurrent()`.
  - A GL window is drawn at most once per frame callback, and an event
    loop with idle callbacks waits for a pending frame (up to 50 ms), so
    a program animating from an idle callback (`fractals`) runs at the
    screen's refresh rate; `swapInterval(0)` draws as often as asked. A
    minimized window, which gets no frame callbacks, never blocks.
  - The overlay is drawn into the back buffer over a freshly drawn scene.
  - A swap postponed to the frame callback is done with the window's own
    context current.
  - `gl_start()`'s surface is cleared once per repaint and swapped after
    the window's `draw()`.
- There are no hardware overlay planes; the overlay is simulated on

### `FL/gl.h`

**Status:** Complete — `fl.opengl` (GL bindings) + `fl.glx` (GLX,
Linux) + `fl.egl`/`fl.wayland_egl` (EGL, Wayland builds) + `fl.gl` (the
functions this header declares)

`fl.opengl` declares OpenGL 1.x with `extern (System)`, so the same
declarations work on Linux and Windows (WGL comes from druntime's
`core.sys.windows.wingdi`). Later GL functions are looked up at run time
(`GL/glew.h`). `fl.gl` has `gl_color()`, `gl_rect()`, `gl_font()`,
`gl_draw()` (7 overloads), `gl_start()`/`gl_finish()`, `glVisual()`
(`Fl::gl_visual()`, kept out of `fl.core`) and the rest.

- `gl_start()` draws into the front buffer, so on X11 and Windows it
  doesn't work in a double-buffered window, whose repaint can overwrite
  it; use a single-buffered window. On Wayland it draws into a surface
  of its own over the window.
- **Text with textures**: each string is drawn into an alpha texture at
  the window's scale (`computeTexture()`/`alphaMaskForString()`, which
  renders at scale 1 in device pixels so the whole texture is filled),
  kept in a bounded FIFO cache.
- **Text without textures**: when the GL driver has neither OpenGL 3 nor
  a texture-rectangle extension, or the program calls
  `fl.core.drawGlTextWithTextures(false)` (at any time; the next
  `gl_font()` or `gl_draw()` follows it), text is drawn with bitmap fonts
  in display lists. On X11 that is a core X font close to the current
  font (`XLoadQueryFont()`, falling back to "fixed") through
  `glXUseXFont()`, so only Latin-1 draws; on Windows the GDI font through
  `wglUseFontBitmapsW()`, 1024 code points at a time. The lists are kept
  per font and size and dropped with the last GL context
  (`gl_remove_displaylist_fonts()`). Wayland has no bitmap fonts for GL,
  so text there always uses textures. GLUT's stroke font, FLTK's last
  resort, is not used.
- Rotated text turns the string's texture about the start of its
  baseline; bitmap-font text is drawn level.
- `test/gl_text.d` shows both text paths and rotated text.

## Text input

### `FL/Fl_Input_.H`

**Status:** Complete — `fl.input_`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Input_.H))

The editing engine of the text fields: `expand()`, word and line
movement, `drawtext()`, mapping mouse positions to text, `replace()`/
`undo()`/`redo()`/`copy()`, input-method text, and `copy()`/`paste()`
through the clipboard.

- The text is a `string` (`size()` is its length), and undo is an array
  of steps.
- UTF-8 helpers come from `fl.text_buffer`.
- Word-wise movement and selection step over letters, digits and
  combining marks of any script, plus `#%-@_~`, a whole character at a
  time.
- The cursor, Delete and Backspace step over one user-perceived
  character, a Unicode grapheme cluster: a whole emoji sequence, or a
  letter with its combining accents (`fl.text_buffer`'s `graphemeLen()`/
  `prevGrapheme()`, on `std.uni.graphemeStride()`).
- `resetSpot()` is called when a field loses focus or is hidden.
- Where the input method's provisional text arrives as marked text
  (`fl.core.hasMarkedText()`, Wayland), it is the selection, drawn
  underlined instead of highlighted, and the next keystroke replaces it.
  `TextEditor`/`TextDisplay` do the same. On X11 and Windows the input
  method shows the text being composed in a window of its own.
- Pasting into a `FloatInput` checks the whole text against a stricter
  pattern than typing does: an exponent is only accepted after a `.`, so
  `1e5` and `0x1F` can be typed but not pasted (`Input_.handle()`,
  `Event.paste`; `FLTK_ISSUES_3.md`).

## Images

Every image format is decoded in D (XBM, XPM, PNM, BMP, ICO, GIF, SVG,
PNG, JPEG); only PNG, `.svgz` and the encoders that compress use zlib
(`std.zlib`).

### `FL/Fl_Image.H`

**Status:** Complete — `fl.image`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Image.H))

The base `Image` and `RGBImage` (1 to 4 channels), with alpha blending
of 2- and 4-channel images over the background, and bilinear or
nearest-neighbor resampling (`RGBScaling`).

- `draw()` draws at `w()`/`h()` times `fl.core.currentScale()` device
  pixels, always resampled from the original pixels: when that equals the
  image's own size (for instance a 2× icon at 200%) the pixels are used as
  they are; otherwise a copy resampled bilinearly (`scalingAlgorithm()`)
  is made once per size (`scaledCache_`) and drawn 1:1 with
  `fl.draw.drawImageFixed()`. `rgbScaling()` applies to a program's own
  `copy()` calls.
- `RGBImage.array` is a D slice, so there is one constructor, and the GC
  owns the memory.
- Each subclass exposes its own typed data (`RGBImage.array`, ...); there
  is no generic `data()`/`count()`.
- No colormaps, and no negative `ld()` on an `RGBImage` (the raw-buffer
  `fl.draw.drawImage()` accepts negative deltas).
- `fail()` returns `errMemoryAccess` when the data given to `RGBImage`
  or `Bitmap` is too short for its size; a negative `ld()` holds the
  error code.
- `RGBImage.maxSize()` (the size limit the BMP, ICO, PNM, PNG and JPEG
  loaders check), `asSharedImage()`, `asSvgImage()`.
- Not ported: `draw_scaled(X, Y, W, H)` (deprecated; use `scale(W, H,
  false, true)` then `draw(X, Y, W, H)`) and `label(Fl_Widget*)`/
  `label(Fl_Menu_Item*)` (deprecated; use `Widget.image()`/`deimage()` or
  `MenuItem.image()`).

### `FL/Fl_Pixmap.H`

**Status:** Complete — `fl.pixmap`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Pixmap.H))

Color-table (XPM) images with transparency, including FLTK's "compressed"
colormap form.

- A color is opaque or transparent (`None`), drawn on X11 with a 1-bit
  clip mask built from the same buffer as the pixels, so the two always
  line up. Through a driver without a GC (GL, Cairo, the file surfaces)
  the pixmap is drawn as an RGBA image instead.
- `colorAverage()`/`desaturate()` build new color strings.
- `draw()` resamples from the original XPM data to `w()`/`h()` times the
  current scale, once per size (`scaledForDraw()`/`scaledCache_`), and
  draws the result 1:1; at the image's own size nothing is resampled.

### `FL/Fl_Shared_Image.H`

**Status:** Complete — `fl.shared_image`
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_Shared_Image.H))

A reference-counted image cache keyed by file name. Every format fldtk

PNG, JPEG and SVG. Handlers added with `addHandler()` are tried before
the built-in GIF-to-SVG formats, so a program can add a format or take
one over. `registerImages()` does nothing and is deprecated, kept so
programs that call it still compile. A
PNG, JPEG or SVG image made from memory with a name is added under that
name (`SharedImage.addNamed()`), so `get(name)` and a `HelpView`
`<img src>` find it.

- The pool is an array searched linearly.
- The `copy()` that only adds a reference is `retain()`.
- `compare()` (name, then width, then height) is a static function.

### `FL/Fl_JPEG_Image.H`

**Status:** Complete — `fl.jpeg_image` (+ `fl.jpeg_decoder`,
`fl.jpeg_encoder`, `fl.jpeg_common`)
([header](https://github.com/fltk/fltk/blob/master/FL/Fl_JPEG_Image.H))

`JpegImage : RGBImage` (always decoded to 8-bit RGB) and `writeJpeg()`.

- The codec implements Rich Geldreich's public-domain jpgd/jpge,
  following Ketmar's D translation in `arsd`'s `jpeg.d`, with GC arrays,
  `JpegException` and validated input; it produces the same pixels and
  bytes as that original.
- Decoding: baseline and progressive 8-bit Huffman JPEGs with 1 (gray) or
  3 (YCbCr) components and H1V1, H2V1, H1V2 or H2V2 subsampling.
  Arithmetic coding, 12-bit samples and CMYK/YCCK are rejected.
- Encoding: baseline JPEGs from 1-, 3- or 4-channel pixels, with
  optimized Huffman tables (the default; two passes), quality 1–100 and
  any of those subsamplings.
- H2V2 chroma is upsampled in the frequency domain, so pixels differ from
  libjpeg's slightly (a mean of 0.18–0.66 per channel out of 255 against
  ImageMagick on two real JPEGs). EXIF orientation is not applied.
- Tested with round trips (within a tolerance) and against ImageMagick's
  decode of real files.

### `src/drivers/Cairo/` — `Fl_Cairo_Graphics_Driver` / `Fl_X11_Cairo_Graphics_Driver`

**Status:** Complete — `fl.cairo_graphics_driver` (+ the Cairo mode in
`fl.draw`), Cairo build

`CairoGraphicsDriver` draws every `fl.draw` primitive through Cairo and
lays out and draws text through Pango. It draws everything on Wayland,
and on X11 when the `Graphics` startup setting is `cairo`: the
environment variable `FLDTK_GRAPHICS=cairo`, or the Graphics setting in
`fldtk-options` (otherwise X11 drawing uses Xlib and Xft).

On X11 in Cairo mode:
- `setDrawable()` gives the driver a Cairo context for the window or
  pixmap, one `cairo_xlib_surface` per drawable, made on first use,
  resized when the drawable's size changes, and freed with it.
- Fonts and text measurement go to Pango. The built-in fonts use Pango
  names ("Sans", "Monospace Bold", "Standard Symbols PS", ...); a renamed
  or added font's style character becomes a Pango style suffix
  (`pangoFontName()`).
- The clip comes from `fl.draw`'s clip stack, replacing Cairo's clip each
  time, and the translation goes into the driver's matrix.
- `XCopyArea()` (double buffering, `fl_scroll()`, offscreen copies),
  `XGetImage()` (`readImage()`, image surfaces) and the overlay rectangle
  still use Xlib; pending Cairo drawing is flushed first.
- `SurfaceDevice` falls back to the Cairo driver for a surface without a
  driver of its own.

Details (see the module's top comment):
- The clip, filled rectangles, thin horizontal and vertical lines and
  rectangle outlines are rounded down to whole device pixels, so nothing
  is left unpainted next to pixels copied with `XCopyArea()` at 110% or
  133%.
- Vertex paths arrive as device-pixel points, rounded to whole pixels.
- Images arrive as buffers, and a Cairo pattern is made for each draw.
- Indexed colors are opaque.
- Text is placed on the baseline Pango reports for the layout being drawn
  (`pango_layout_get_baseline()`), so a character from a fallback font
  with a larger ascent (CJK, emoji) doesn't push the line down and get its
  bottom clipped.
- `setFonts()` lists every face in Pango's font map, each under its own
  name ("DejaVu Sans Condensed" bold, "DejaVu Sans ExtraLight"), read with
  `LANG=C` so the face names are untranslated
  (`pangoFontNames()`).
- The focus rectangle is a 1-unit dotted line through the driver's
  line-style and rectangle calls. The overlay rectangle is drawn and
  erased with Xlib on X11, with the driver's drawing flushed first and
  the drawable marked changed afterwards; on Wayland it is copied in the
  window's Cairo buffer.

### `src/drivers/OpenGL/` — `Fl_OpenGL_Graphics_Driver` / `Fl_OpenGL_Display_Device`

**Status:** Complete — `fl.gl_graphics_driver` (+ `fl.gl_display_device`)

`GlGraphicsDriver` draws `GraphicsDriver` calls with OpenGL: colors,
rectangles, lines, polygons, line style, clipping (`glScissor()` with the
rectangle `fl.draw` has already intersected), arcs and pies, vertex
paths, text (`fl.gl.gl_draw()`), rotated text (the string's texture
turned about the start of its baseline; bitmap-font text is drawn level;
`test/gl_text.d`), and images (`gl_draw_image()`, flipped with
`glPixelZoom(1, -1)`, since `RGBImage` rows run top-down).

- Complex polygons are filled scanline by scanline from the edges of
  each sub-loop (`endComplexPolygonParts()`), with no edge between one
  sub-loop and the next, so shapes drawn together and holes fill
  correctly.
- `drawImage()` uses `glDrawPixels()` each time, with no texture cache.
- `drawBitmap()` builds an RGBA buffer in the current color (alpha 255
  or 0 per bit) each time and draws it the same way, at its own size,
  clipped to the visible rectangle.
- With a dash style (`FL_DASH`, `FL_DOT`, ...), lines and rectangle
  outlines are drawn as stippled GL lines, so a focus rectangle is dotted.
  A custom dash array is cut into dash pieces by `stroke()`, in FLTK
  units, the pattern running on along each path
  (`smoke-tests/gl_dashes.d`). Cap and join styles are ignored.

## Fluid (the UI designer / D-source exporter)

Rows follow the subdirectories of FLTK's `fluid/`. The program is
`fluid` (`rdmd buildfluid.d`): `fluid [file.fl]` opens the editor, and
`fluid -c [-o out.d] file.fl` writes D source without opening a window.
`-h`/`--help`/`-help` print usage.

Fluid reads a `.fl` project and writes one D module from it. The editor
shows the project's windows with live `fl.*` widgets, with selection
shared with a tree-shaped node browser, the property panel, the widget
bin (drag and drop onto the canvas; a drop whose text names no widget
type, from another program say, is ignored), moving and resizing with the
mouse, Ctrl+drag to copy,
align and distribute commands, undo and redo, and saving to `.fl`.

How the `.fl` dialect and the generated code work (details in
`FLUID_DIALECT.md`):
- One D module per project, with no header file.
- Callbacks are delegate literals written inline.
- The project is a tree (`Node.children`, `parent`).
- `.fl` files are written with each property block and child block
  opening `{` on its own line, one level deeper than the `Type name`
  header, and the closing `}` under it (`ProjectWriter.writeNode()`).
  The reader ignores layout, so K&R-style files load and are rewritten
  in this style when saved.
- Save As adds `.fl` to a name that doesn't end in it
  (`fluid.path_util.ensureFlExtension()`), and asks before replacing an
  existing file under the new name.
- `use_FL_COMMAND` (Options) makes generated shortcuts use
  `stateCommand`/`stateControl`; otherwise they are written as
  `stateCtrl|'s'` and so on. `do_not_include_H_from_C`, `utf8_in_src` and
  `avoid_early_includes` are read and dropped.
- `mergeback 1` (Options) turns on MergeBack (see `fluid/app/`).
- A widget has three code slots: `setup` (after the widget is made,
  before its children), `finalize` (after its children, before `end()`;
  groups and windows only) and `callback`, stored as
  `WidgetNode.setupCode`/`finalizeCode`/`callback`. An import goes in a
  parent widget's `setup` code or in a `decl` node.
- The `in header`/`in source` controls of `decl`, `class` and `Function`
  nodes are kept in the `.fl` file but change nothing in D output.

File > Run (F5, and the Run button of the widget panel) saves, writes
the code, builds with `dub build` and starts the program, and File > Set
Up dub Project writes or completes the dub.sdl of the design's dub
project (`gui_main.d`'s `runProject()`/`setUpDubProject()`,
`fluid.dub_project`, `fluid.run_program`, `panels/run_window.fl`;
`BUILDING.md`, "Running a design from Fluid"). The Run window shows
dub's output, compiler errors included, and the program's output as
plain text. A `dub.json` recipe is not edited; Set Up dub Project shows
the entries to add.

### `fluid/nodes/` (28 files)

**Status:** Complete — `source/fluid/*_node.d`

The node kinds:
- `Node` (label, callback, user data, comment, open, selected).
- `WidgetNode`, with the properties of nearly every leaf widget.
- `WindowNode` (modal, xclass, noborder, size range, children),
  `GroupNode`, `GridNode`, `FlexNode`.
- `MenuOwnerNode`/`MenuItemNode`.
- `ClassNode`: a class with a base class (a `class Name {}` without one
  is flattened into the module).
- `WidgetClassNode`: a D `class Name : BaseClass` with the named children
  as fields.
- `CodeNode`, `DeclNode`, `DataNode` (code, declarations, embedded data).
- `CodeBlockNode`/`DeclBlockNode`: their children between a "before" and
  an "after" line. `DeclBlockNode` adds braces and indents its children,
  since D's `version()`/`static if` need braces that a `.fl` value can't
  hold unbalanced.
- `FunctionNode`: `main()`, named functions, and a class's constructor,
  destructor and methods.
- `CommentNode`: a comment entry in the tree (with `in_h_`/`in_c_`),
  separate from every node's `comment` property, written where it
  stands: at the top of the file, or in a function body, code block or
  widget class, as a `/* ... */` block.

A class or widget class inside another class is written as a `static`
nested class; a function in a declaration block inside a class is a
method. A unit test at the end of `code_writer.d` generates every node
kind in every container Fluid allows it in, and fails if any of them is
missing from the output.

Properties:
- A widget's `type` is chosen from a table per widget kind
  (`fluid.subtypes`): buttons, Pack, Flex, Scroll, sliders, scrollbars,
  rollers, Input, Output, Spinner, Counter, Dial, Browser and MenuButton,
  edited with the panel's Subtype choice. For windows (Single/Double),
  menu items (Normal/Toggle/Radio) and menu bars (`Fl_Sys_Menu_Bar`) the
  choice picks the class or node kind instead.
- `WidgetNode.access` (the `.fl` flags `private`/`protected`): a
  protection attribute on a class field, `private` on a module-level
  variable. `FunctionNode` has `access` plus `declareC` (`C`): a method
  gets a protection attribute, a plain function `private`, and
  `declare "C"` gives `extern (C)`.
- `ClassNode.prefix` (`class final Foo {` in the `.fl` file) is written
  before `class`: `final class Foo`. The panel's Attribute field edits it.
- An inline-data node without a file name generates an empty array; one
  whose file can't be read generates `static assert(false, "Can't include
  data from file. Can't open ...")`, alerts on Write Code, and is printed
  as `FLUID ERROR:` by `fluid -c`.
- `DataNode`'s storage is two flags, `asString` and `compressedFlag`,
  which combine freely (the panel's "Storage Format:" group). In `.fl`
  files they are `textmode` and `compressed`; `std_binary`/
  `std_textmode`/`std_compressed` are read but not written.
- Grid cells (`location`, `colspan`, `rowspan`, `align`, `minsize`) are
  read from a child's `parent_properties` block, which the reader hands
  to the parent node to interpret.
- A `widget_class` with `position_relative`/`position_relative_rescale`
  ends its constructor with `position(x, y)`/`resize(x, y, w, h)`.

On the canvas:
- A `Grid` is a `fluid.grid_proxy.GridProxy`: selecting it, or dragging
  a child, shows its cell lines in the overlay. Grid and Grid Child tab
  edits go to the live grid (`fluid.instantiate.syncLayoutToLive()`), and
  the node takes what the grid accepted. A `Flex`'s fixed sizes are
  applied the same way (`syncFlexToLive()`).
- Dragging, resizing or arrow-keying a grid or flex child hands it to the
  container (`fluid.layout_edit`): a grid child moves to the cell under
  the pointer or one cell per arrow key, and resizing sets its cell's
  minimum size; a flex child moves to the nearest slot or one place per
  arrow key, and resizing gives it a fixed size. The nodes are then
  updated from the live containers (`syncLayoutFromLive()`: rectangles,
  cells, order, fixed sizes) after inserts, paste and duplicate (a pasted
  grid child takes the next free cell), panel edits and drags, and before
  saving or writing code.
- A `Scroll` is a scrollable `fluid.scroll_proxy.ScrollProxy`. Nodes keep
  unscrolled coordinates and live children sit at node minus scroll
  position; `fluid.instantiate`'s `scrollOffsetAbove()`/
  `scrollOffsetWithin()`/`geometryFromLive()`/`syncDescendantsFromLive()`
  convert between them. Moving or resizing a container writes its
  descendants' geometry back to their nodes. `ScrollProxy` repaints the
  whole canvas window on every scroll. Rebuilding the canvas for undo or
  redo keeps each `Scroll`'s position (`ProjectCanvas.rebuildFrom()`,
  matched by node `uid`); reopening a file starts at 0.
- Images: XPM and GIF are embedded as pixmaps and XBM as bitmaps; other
  formats as their compressed bytes with `compress`, or as decoded RGB
  pixels without. `bind_image`/`bind_deimage` (`Widget.bindImage()`/
  `bindDeimage()`) and `scale_image`/`scale_deimage` (`Image.scale()`)
  apply in generated code and on the canvas alike.
- The "..." button by the Image and Inactive fields opens the Image
  Options dialog (`makeImagePanel()`/`propagateLoadImagePanel()`/
  `runImagePanel()` in `panels/widget_panel.fl`): width and height with a
  Reset button, "convert to raw pixel data" (the inverse of `compress`)
  and bind, for both images, written to the selected nodes. It shows the
  image file's own size (`SharedImage.get()`).
  Changing the scale there updates the widget on the canvas at once.

- **`Image_Asset.h`/`.cxx`**: see `fluid/nodes/`.
- **`i18n.h`/`.cxx`**: `fluid.i18n.I18nSettings`, read, written and used
  by the code writer: labels and tooltips (menu items included) are
  wrapped in the configured `gettext()`- or `catgets()`-style call. The
  include field is a D module name, written as an `import`; with a
  conditional set, it goes in `version (<conditional>)` with
  pass-through functions in the `else` branch. A C-style include from an
  FLTK `.fl` file is written as a comment. Menu items are translated at
  the array element, since the generated `MenuItem[]` is built at run
  time. fldtk ships no translation module (see "Not ported" above).
- **`mergeback.h`/`.cxx`**: `fluid.mergeback` (`Mergeback`, `Crc32`,
  `formatTag()`), the tag writing in `code_writer.d`, and
  `ProjectSettings.writeMergebackData`.
  - With the project flag on, each `code {}` fragment, widget and
    menu-item callback, and widget `setup` and `finalize` code is put
    between CRC-tagged `//` lines. `Mergeback.analyse()`/`apply()`
    recompute the CRCs from a generated file, report edits, and copy
    edited blocks back into the nodes by `uid`.
  - `&File/MergeBack Code` (shown only with the flag on) asks before
    merging; merging also runs when a project is opened and when the
    program is activated (`Event.appActivate`, X11 under an EWMH window
    manager). The last code file written for a project is remembered
    (`rememberCodePath()`, also by `fluid -c`), so a file generated by a
    build step is found.
  - Blocks keep their indentation and are un-indented by the tag line's
    indentation. `setup` and `finalize` code is written with the widget's
    name (`this` in a widget class) for `o`, and merged back with `o`
    (`fluid.code_highlight.renameIdentifier()`): only uses as code are
    renamed, not text in strings, character literals or comments, and
    not a member access (`x.o`). Merging back also turns a use of the
    widget's name that was written out in the `.fl` file into `o`, which
    means the same. D's token strings (`q{...}`) count as code.
    `FINALIZE` blocks are written for every widget, and menu-item
    callbacks merge back.
  - Command line: `-m`/`--merge-back`, `-mb`/`--merge-back-if-safe` and
    `-mi`/`--merge-back-info` (`compile.d`'s `mergeBackProject()`) merge
    into the `.fl` file and save it (the info mode only reports), exit
    with 1 on an unreadable tag or an unsafe `--merge-back-if-safe`
    merge, and combine with `-c` to merge before regenerating.

  - **Help:** Rapid development with FLUID..., FLTK Programmers
    Manual..., About.

    them.
- **Placing new nodes** (`placeNewNode()`): from the selection (as its
  last child if it can hold children, else right after it), climb to the
  nearest parent the new kind may live in (`acceptsNewNode()`): a menu
  item in a menu widget or submenu; Code in a Function, Code Block,
  Widget Class or group; Code Block and Comment in a code block; Window
  in a Function or Code Block; Function, Declaration, Inline Data,
  Declaration Block and Class in a Declaration Block or Class; Widget
  Class likewise but not inside another Widget Class. Other kinds go to
  the top level (after the selection's top-level node, or first).
  - Menu items, Code, Code Block, Window and widgets need such a parent;
    when there is none, `assistNodeCreation()` offers to create it: a
    Function (or a method of the selected class) for Code, Code Block and
    Window; a Window, and a Function if needed, for a widget; a Menu
    Button (a Menu Bar for a submenu) with its Window and Function for a
    menu item. The whole creation is one undo step; declining creates
    nothing.
  - Paste places each node the same way (widgets need a group or
    window; a node with no place is skipped); with nothing selected it
    pastes into the active window.
  - A new Widget Class gets a window's starting geometry (480×320,
    centred) and its own canvas.
- **New node defaults:** a widget gets FLTK's default label
  (`instantiate.d`'s `defaultLabelFor()`), a code node a D default
  (`defaultNameFor()`: `makeWindow()`, `writeln("Hello, World!");`,

  `UserInterface`). A new menu item is "item" (a submenu "submenu"); a new
  Menu Button, Choice or Input Choice is labelled "menu", "choice:" or
  "input choice:", and shows a one-item "CHOICE" menu until it has items.

  live menu whenever an item is added, deleted or edited
  (`refreshLiveMenu()`, `refreshLiveMenuOf()`). An item without a label
  shows "(nolabel)" and is generated with an empty label. Item flags
  (value, deactivate, hide, divider, headline, submenu, toggle, radio)
  apply on the canvas and in generated code, and shortcuts and images
  show in the canvas menu. Clicking an unselected menu widget opens its
  menu, and the picked item is selected and opened in the property panel.
  In the property panel a menu item has position, alignment, label
  margins, box, colors, text style, class and When inactive; Down Box
  active; Value and Shortcut active except on a submenu, which also has
  no subtype.
- **Keys on the canvas:** a canvas window tests every shortcut only
  against Fluid's main menu (`ProjectCanvas.onShortcut`), and keeps
  pointer-crossing and focus events from the design's widgets, so none of
  them takes a key from Fluid.
- **Snap_Action** (`fluid.snap_action`): moving with the mouse,
  resizing from eight directions, arrow-key nudging and rubber-band
  selection, each an undo step. All 30 of FLTK's snap actions (window and
  group edges and margins, tabs margins, which replace the group margins
  inside a `Tabs`, sibling alignment, ideal widget size, window and group
  grids with the grid dots drawn while dragging) snap and draw when
  guides are shown (`ProjectCanvas.showGuides`). Resizing a selection
  moves the widgets on the dragged edge with it and keeps the others
  within the new bounds. Moving the selection with Ctrl held moves a copy
  of it instead, made the way Duplicate makes one, and the copy and its
  move are one undo step; whether a drag copies is decided when the mouse
  first moves.
- **shell_command:** `fluid.shell_process` runs a command
  (`std.process.pipeShell()`), expands macros and streams the output
  through `addFd()` and a timer; `fluid.shell_command`
  (`ShellCommand`/`ShellCommandList`) holds the named commands

- **Starting and New:** a new project is empty (no nodes), titled
  "Untitled.fl" until it has a file name, and the editor starts in that
  state, so a Function and a Window can be added at once. Selecting and
  opening a node works without any canvas.

### `fluid/tools/`

**Status:** Complete

- **`filename.h`/`.cxx`**: `path_util.d` (`filenameShortened()` and the
  rest), working on code points. `History` shortens recent-file paths to
  48 characters for the menu (`History.relpath[]`). Two edge cases FLTK
  gets wrong are handled (see `FLTK_ISSUES_n.md`).
- **`ExternalCodeEditor_UNIX.h`/`.cxx`**: `external_code_editor.d`
  (`ExternalCodeEditor`) starts an external editor for a code node
  (`std.process.spawnProcess()`), watches the file for changes and reaps
  the process when it exits. The property panel's Code section has an
  "Edit Externally..." button, and the Settings General tab has "External
  Editor:" and "Use for Code Nodes". `gui_main.d` keeps one editor per
  code node and a 2-second timer that takes in changes from all of them.
  The same code is used on Windows (`ExternalCodeEditor_WIN32` is not
  ported); the temp files go under `std.file.tempDir()`. It works with
  Notepad on Windows and with `vi`, `nano`, `mc -e`, KWrite and Kate on
  Linux: a save comes back into the node at once, and a command that
  can't be started gives an alert. A terminal editor runs in the
  terminal Fluid was started from; when Fluid was started without one,
  the command has to open a terminal itself (`konsole -e nano`).
  Quitting the editor without saving leaves the node as it was. Watching
  ends when the editor process does, so an editor that passes the file
  to a copy of itself that is already running, and exits at once, is
  not watched at all: what is saved there never reaches the node. Such
  editors need their wait option (`kate --block`, `code --wait`). The command is split at
  spaces, so an editor path containing spaces doesn't work.
- **`autodoc.h`/`.cxx`**: not ported (see "Not ported" above).

### `fluid/widgets/`

**Status:** Complete

Fluid's own widgets, built on `fl.*`.

- **Node browser** (`node_browser.d`): `NodeBrowser` is a `fl.tree.Tree`,
  which fits the tree-shaped project. Its rows are `NodeBrowserItem`s
  (`calcItemHeight()`/`drawItemContent()`): the class name in bold
  without `Fl_`, then the instance name, or the label in quotes; an
  optional dark green comment line above; a thin line under each
  unselected row. Function, top-level or in-class Code Block, Comment and
  the other code nodes have their own single-part rows in the User tab's
  fonts and colors (`rowKind()`/`nodeTitle()`). The type icon gets a lock
  for a private widget or function, a mark for a protected one (never on
  a declaration or declaration block), and an "invisible" mark for a
  hidden widget outside a Tabs or Wizard. Selecting on a canvas scrolls
  the browser to the selected row (`syncSelection()`). The browser shows
  every top-level node of the project.
- **Widget bin** (`panels/function_panel.fl`, the "Widget Bin" window):
  all 8 groups and 57 buttons. Each group's buttons sit on a 24-pixel grid
  in an inner group they fill completely, as `compact()` buttons, so each
  group draws as one bar; empty grid places are blank buttons. Each
  button's icon is an `image` line in the `.fl` file naming its SVG in
  `pixmaps_svg/`, and its `setup` code sets its node type
  (`BinButton.typeName()`). `BinButton` adds its
  widget on a click or by dragging it onto a canvas (XDND drag source);
  the 9 Code buttons are click-only; the 4 menu-item buttons can be
  dropped on a menu widget or submenu. The Window button
  (`Bin_Window_Button`) creates a window on a click, or, dragged, shows a
  borderless preview following the pointer and creates the window where it
  is dropped on the desktop (`fluid.bin_button.onWindowDropped`).
- **Icons** (`fluid.pixmaps`, `pixmapFor()`/`loadPixmaps()`): one per
  node type, used by the browser rows (`TreeItem.usericon()`) and the
  New menu; the bin buttons load the same files through their `image`
  lines. They are SVG redrawings of FLTK's
  `fluid/pixmaps/*.xpm` (`source/fluid/pixmaps_svg/`, embedded with a
  string import), drawn by `SvgImage` at the screen's scale.
- **Which widgets the bin and New menu offer:** every widget kind
  including `Pack`, `Scroll`, `Tile`, `RepeatButton`, `TextEditor`,
  `FileInput`, `Tree`, `CheckBrowser`, `HelpView`, `FileBrowser`, `Table`
  and `Progress`, registered in `fluid.factory`/`fluid.instantiate`, with
  a Browsers category in the New menu. `Tree` and `HelpView` are leaf
  nodes (they hold no designed children). `Table` is a `GroupNode`: on the
  canvas a `fluid.table_proxy.TableProxy` with 14 rows and 7 columns of
  sample data, it accepts children (the first one brings FLTK's "not
  recommended" message), and generated code creates a plain `Table`.
- **Adding nodes:** code nodes through `addNode()`, widgets through
  `insertWidget()`/`addWidget()` ("Please select a group widget or
  window" when there is no place for one), windows through
  `createWindowNode()` (in the nearest Function, Code Block or window, or
  offering to create a Function). A window created inside another window
  is a subwindow at 10,10, 480×320 capped to fit its parent; its canvas is
  built inside its parent's (`nestedWindowFactory`,
  `registerNestedCanvases()`), its children are relative to it, and
  generated code creates it with `Window(x, y, w, h)`. Every top-level
  window has its own canvas (`canvases_`). The current selection is the
  active canvas's, or the browser's when there is no canvas
  (`currentSelection()`). A new node opens in the property panel
  (`openNode()`), as does double-clicking a row.
- **Change To** (`fluid.change_type`): a widget changes into another
  kind of its family in place: text fields and number widgets (one
  family), buttons, menus, and Group/Pack/Scroll/Tabs/Tile/Wizard. It
  keeps its place, geometry, label, name, callback and every property
  the new kind also has; the rest is cleared. Flex and Grid, and kinds
  outside these families, can't change kind. It is offered in the
  project tree's right-click menu (which also holds Cut, Copy, Paste,
  Duplicate, Delete, Earlier and Later), in the canvas's right-click menu
  on a selected widget (next to New), and as "Change to:" on the Style
  tab. Each change is one undo step.
- **New widget geometry:** each type gets its size from the active
  layout preset (`fluid.instantiate.idealSizeFor()`, `fluid.layout_suite`
  with FLTK's "FLTK" and "Grid" suites, and user suites stored in the
  preferences, the project or a `.fll` file). A widget dropped into a Flex
  goes to the nearest slot; into a Grid, the cell under the drop or
  right-click point, else the first free cell
  (`GridProxy.moveCell()`, recorded in `GridNode.cellOf`). A menu bar as a
  window's first child spans its width. `Node::layout_widget()` is not
  ported; the live Grid and Flex lay themselves out.
- **Formula input** (`fluid.formula_input.FormulaInput`): an integer
  formula field (unary `+`/`-`, `+ - * /`, parentheses, variables, wheel
  to adjust); `value()` evaluates and `text()` is the string. The
  property panel's X, Y, W and H fields use it (through the `class
  FormulaInput` override), with FLTK's variables `i`, `x`, `y`, `w`, `h`,
  `px`, `py`, `pw`, `ph`, `sx`, `sy`, `sw`, `sh`, `cx`, `cy`, `cw`, `ch`
  read from the canvas; `i` is the widget's index in the selection. The
  Image Options scale fields use it without variables (a name is then
  0).
- **Code highlighting** (`fluid.code_highlight`, from `Code_Editor`/
  `Code_Viewer`/`Style_Parser`): a D lexer (`styleParse()`) with token
  classes following nano's `d.syntax` and colors for a white background,
  `enableHighlighting()` (a style buffer for any `TextDisplay`, restyled
  on each change) and `enableAutoIndent()` (Enter keeps the indentation).
  Used by the panel's D code fields (callback, setup code, code and decl
  text, function name and return type) and Code View's Source pane.
  `fluid.code_viewer.CodeViewer` draws the selection in light gray, so
  the node highlight stays readable over the colors.
- Not ported: `App_Menu_Bar` and `Text_Viewer`.
