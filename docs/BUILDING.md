# Building fldtk

Requirements: a D compiler (dmd, ldc or gdc) and dub. Every build step
here is either dub or an rdmd script, both of which ship with a standard
D install on every platform D supports. On Linux the library links the
X11/GL libraries every desktop has (with libXi, for touch), plus Cairo and Pango (the
development packages: libcairo2-dev and libpango1.0-dev, or cairo-devel
and pango-devel) and, for the Wayland backend, libwayland-client,
libwayland-cursor, libwayland-egl, libEGL and libxkbcommon
(libwayland-dev, libegl-dev and libxkbcommon-dev, or wayland-devel,
libglvnd-devel and libxkbcommon-devel); see "Cairo and Pango support" below for building
without them, which also leaves out Wayland.

A Linux program uses Wayland when a Wayland compositor is running and
X11 otherwise, as FLTK does. The Backend setting in `fldtk-options`
chooses one for every program, and the environment variable
`FLDTK_BACKEND=x11` or `FLDTK_BACKEND=wayland` forces one for a single run
(in any case: `X11` works too). `PORTING.md`'s `FL/wayland.H` row lists
what the Wayland backend doesn't do yet.

From the repo root:

    dub build              # the fl.* library -> ./libfldtk.so
    rdmd buildfluid.d      # the Fluid editor  -> ./fluid
    rdmd buildsamples.d    # the demo programs -> ./build/
    dub build fldtk:options  # the options program -> ./fldtk-options

All four are incremental: each checks whether its output is missing or
older than the sources it is built from, and does nothing if it is
already current.

The file names above are the Linux ones; on Windows the outputs are
fldtk.lib, fluid.exe, build\*.exe and fldtk-options.exe. See the Windows
section below.


## The library

    dub build

Compiles source/fl/ into libfldtk.so in the repo root.


## Fluid

    rdmd buildfluid.d

Builds ./fluid, the UI designer. Fluid's own interface panels are
themselves Fluid documents (source/fluid/panels/*.fl), so this script
also regenerates source/fluid/panels/generated/*.d from them whenever one has
changed -- including on a fresh checkout, where none of them exist yet
and a temporary bootstrap build of Fluid is made to produce them.

Run it after editing any panels/*.fl. It is the only supported way to
build Fluid; a direct `dub build fldtk:fluid` works only once the
generated panels are already present.

    fluid file.fl          # open the interactive editor
    fluid -c file.fl       # generate file.d instead
    fluid -c -o out.d file.fl
    fluid -m file.fl       # merge edits made in the generated file.d back into file.fl
    fluid -mb file.fl       # same (--merge-back-if-safe), but only if nothing conflicts
    fluid -mi file.fl       # only report what -m would merge (--merge-back-info)

The merge options need `mergeback 1` in the project (Settings, Project tab). They
read the code file last written for the project, or the one named with -o,
and combine with -c to merge first and then regenerate.


## fldtk-options

    dub build fldtk:options

Builds ./fldtk-options, which shows and changes the settings every fldtk
program reads when it starts, for you or for every user of the computer:
visible keyboard focus, arrow-key focus, tooltips, dragging text, the
scheme, the zoom and its display, and on Linux the backend (X11 or
Wayland) and the X11 graphics (Xlib or Cairo). The demo program's
"Runtime Options" button starts it. It also works without a window:

    fldtk-options -L                     # list every value
    fldtk-options -UshowTooltips=off     # change your own value
    fldtk-options -UshowTooltips=default # remove it again
    fldtk-options -Uscheme=gleam -Uzoom=1.5
    fldtk-options -h                     # all switches and settings

Your value comes before the system value. For the scheme, zoom, backend
and graphics an environment variable comes before both, for a single run
or a script: `FLDTK_SCHEME`, `FLDTK_SCALING_FACTOR`, `FLDTK_BACKEND`,
`FLDTK_GRAPHICS`. Ctrl +/-/0 in any fldtk program store your zoom.


## The demo programs

    rdmd buildsamples.d               # everything
    rdmd buildsamples.d test          # only source/test/
    rdmd buildsamples.d examples      # only source/examples/
    rdmd buildsamples.d test hello    # a single program

Binaries land in ./build/ under their own names (./build/hello,
./build/table_sort, ...), and run from anywhere -- each is linked with a
relative rpath back to libfldtk.so in the repo root.

A program is simply a .d file under source/test/ or source/examples/
that defines main(); helper modules alongside them are pulled in
automatically by whichever program imports them. Programs whose UI comes
from a .fl file have their .d regenerated by Fluid first, as needed.

One program is knowingly skipped and reports why when you build: forms
(the XForms compatibility layer, out of scope).

cairo_test and cairo_draw_x build either way, like FLTK's own: without
Cairo support they just show a message saying they need it. See the next
section.


## Cairo and Pango support (Linux)

Linux builds include Cairo support by default, the equivalent of FLTK's
CMake option FLTK_OPTION_CAIRO_WINDOW: CairoWindow (a window drawn
entirely with Cairo), cairoMakeCurrent()/cairoCc()/cairoFlush() for
Cairo drawing in any window's draw(), and the whole Cairo C API
(fl.cairo_c: cairo.h plus the PDF, PostScript, SVG, script and tee
surfaces). They also include the whole Pango C API (fl.pango_c, and
fl.pango_c_cairo for laying out and drawing text on a Cairo context),
with the part of GLib it needs (fl.glib_c). Windows builds leave both out
unless asked; see "Cairo and Pango on Windows" below.

To build without both, so the library needs nothing beyond X11/GL, use
dub.sdl's linux-no-cairo configuration:

    dub build --config=linux-no-cairo        # libfldtk.so without Cairo and Pango
    rdmd buildsamples.d --no-cairo           # the same, plus every demo program

Either way the result is the same libfldtk.so, and a program that uses
neither runs against both. A program that uses Cairo or Pango is
compiled with -version=FLDTK_HAVE_CAIRO -version=FLDTK_HAVE_PANGO and
linked with the libraries it calls:

    dmd -Isource -version=FLDTK_HAVE_CAIRO -version=FLDTK_HAVE_PANGO example.d \
        -L-L. -L-lfldtk -L-lcairo -L-lpangocairo-1.0 -L-lpango-1.0 -L-lgobject-2.0 -L-lglib-2.0

Built against a library made without them, such a program fails at link
time (fldtk's Cairo and Pango modules are missing), never at run time.

A dub project depending on fldtk gets both versions and all of these
libraries automatically from the default configuration, and opts out
with `subConfiguration "fldtk" "linux-no-cairo"`.

A dub project normally selects fldtk's `program` configuration
(`subConfiguration "fldtk" "program"`, see `docs/TUTORIAL02.md`): its
program links the libfldtk.so in the fldtk folder and loads it from
there, so rebuilding fldtk updates every such program. With any other
configuration, dub copies libfldtk.so next to the program.


## Building your own program in Linux (e.g. an exported .d file from a fluid project)

(For Windows, see the Windows section below.)

A program written against fldtk, or generated by `fluid -c`, is a single
.d file with `import fl;` at the top. It needs two things: the compiler
must find the `fl.*` modules (source/fl/), and the linker must find
libfldtk.so, so run `dub build` in the repo root first. The examples
below assume the program is example.d and is compiled from the repo root.

**With a symlink `fl` -> source/fl next to example.d** (dmd searches the
current directory for imports, and `import fl.widget;` then finds
fl/widget.d through the link):

    ln -s source/fl fl                 # once; from the directory holding example.d
    dmd example.d -L-L. -L-lfldtk

**Without the symlink**, name the import root on the command line
instead (`source`, the parent of `fl/`, not `source/fl`):

    dmd -Isource example.d -L-L. -L-lfldtk

If example.d lives elsewhere, use absolute paths for both, e.g.
`dmd -I/path/to/fldtk/source example.d -L-L/path/to/fldtk -L-lfldtk`. (In
the symlink form, make the link from that directory:
`ln -s /path/to/fldtk/source/fl fl`.)

Either way, libfldtk.so is not found at run time unless you tell the
loader where it is. Pick one:

    LD_LIBRARY_PATH=$LD_LIBRARY_PATH:. ./example     # per run
    dmd ... -L-rpath=$PWD                            # baked in at link time
                                                     # (absolute path to the
                                                     # dir holding libfldtk.so)

Do not write `LD_LIBRARY_PATH=. ./example` if you already have
LD_LIBRARY_PATH set (e.g. for Phobos): that replaces it.


## The dub single-file-package header

`fluid -c` can put a dub comment at the very top of the generated .d
file:

    /+ dub.sdl:
    dependency "fldtk" path="."
    subConfiguration "fldtk" "program"
    +/
    import fl;
    ...

`path` is the location of the fldtk folder: the one given in the
editor's Settings > General > fldtk Folder, else the folder `fluid`
itself is in, else the nearest folder above the .d file whose
`dub.sdl` names the package `fldtk` (`.` when the .d is in the fldtk
folder itself). It is relative to the directory of the generated .d
file, as dub reads it, when that goes up at most three folders, and
absolute otherwise. If no fldtk folder is found it falls back to `.`,
so edit it by hand.
`subConfiguration "fldtk" "program"` selects fldtk's configuration for
programs: the program links libfldtk.so in the fldtk folder and finds
it there when it runs.

To turn it on, either:

- pass `--dub-header` on the command line (it only adds the header;
  there is no flag to force it off):

      ./fluid -c --dub-header example.fl              # writes example.d
      ./fluid -c --dub-header -o example.d example.fl

- or tick "Dub single-file-package header" in the interactive editor
  under Settings -> Project. The choice is saved in the .fl file as
  `dub_header 1`, so every later export, including plain `fluid -c
  example.fl`, adds the header.

Then build with dub's single-file mode; no `-I`, no symlink and no
linker flags are needed, since dub gets all of that from the dependency
(the library is rebuilt first if it is out of date):

    dub build --single example.d           # builds ./example next to example.d
    dub run --single example.d             # builds and runs

The header only matters to dub. `dmd example.d ...` and `rdmd
example.d` treat it as a comment and ignore it, so use the command lines
from the previous section for those. `docs/TUTORIAL01.md` walks through
both ways.


## Running a design from Fluid

File > Run (F5), or the Run button in the widget properties panel,
saves the project, writes the code file, builds the program with `dub
build` and starts it. The Run window shows the build's output and then
the program's; Stop ends either, and the next Run ends a program still
running from the last one. `dub` must be on the PATH.

What gets built depends on the dub header and on where the .fl file is:

- **With the dub header on:** the code file alone (dub's single-file
  mode, `dub build --single`), without asking, even inside a dub
  project. File > Set Up dub Project turns the header off.
- **In a dub project** (the nearest folder at or above it with a
  `dub.sdl` or `dub.json`, not counting the fldtk folder itself): that
  project, once its recipe depends on fldtk and the Code File is in its
  `source/` folder. If either is missing, Run offers to set it up.
- **In no dub project:** Run asks whether to set one up in the .fl
  file's folder, or to build the code file alone, which turns on the
  dub header above.
  A design in the fldtk folder (`docs/TUTORIAL01.md`'s, a sample's) is
  always built as a single file: Set Up dub Project refuses that folder,
  whose `dub.sdl` is fldtk's own.

File > Set Up dub Project does the setting up on its own. In a folder
with no recipe it writes what `dub init -n -f sdl` would (`dub.sdl`,
`.gitignore`), with the dub.sdl also holding the lines this design
needs: `targetType "executable"`, the `fldtk` dependency with the full path of the fldtk folder,
`subConfiguration "fldtk" "program"`, and the `preGenerateCommands`
that run `fluid -c` on the design; an existing `dub.sdl` gets the lines it lacks, and is
left alone otherwise. It moves the Code File to `source/<name>.d`
unless it already is in `source/` or `src/`, asking first when that
file exists, and removes the untouched placeholder `source/app.d` of
`dub init`, whose `main()` would clash with the design's. A design in a
subfolder of a dub project is added to that project only after Fluid
has said what will change and you confirmed it. Fluid doesn't edit a
`dub.json`; it shows the entries to add instead.

Fluid finds the fldtk folder as the dub header does (Settings > General >
fldtk Folder, else the folder `fluid` is in).

The program's output shows line by line: Fluid sets
`FLDTK_FLUSH_OUTPUT` for it, and a program built with fldtk then writes
each line of `stdout` at once (`fl.output_buffering`). Set the variable
yourself for the same effect when a program's output goes to another
pipe.


## Windows

The same four commands work on Windows with dmd (64-bit). No Visual
Studio or Windows SDK is needed: every system library fldtk uses comes
from dmd's own bundled import libraries. (Cairo and Pango are the
exception; see "Cairo and Pango on Windows" below.)

    dub build              # the fl.* library -> .\fldtk.lib
    rdmd buildfluid.d      # the Fluid editor  -> .\fluid.exe
    rdmd buildsamples.d    # the demo programs -> .\build\*.exe
    dub build fldtk:options  # the options program -> .\fldtk-options.exe

What differs from Linux:

- **The library is static, and there is no DLL.** `dub build` uses
  dub.sdl's `windows-default` configuration, which produces fldtk.lib,
  and every program links it in. A Windows DLL only exports the symbols
  explicitly marked `export`, and the `fl.*` modules are not written
  that way; supporting a DLL would mean adding `export` throughout
  essentially every .d file under source/fl/. That is not planned:
  static linking is the supported Windows build. A side effect is that
  there is nothing to tell the loader about -- programs run from
  anywhere, without the rpath/LD_LIBRARY_PATH setup Linux needs.
- **One more demo is skipped**: list_visuals, which dumps X11 visuals
  and has no Windows equivalent.
- **Release builds** (`--config=linux-release`, `buildsamples.d
  --release`) are Linux-only; see the release section below.

**Building your own program.** With fldtk.lib built, compile from the
repo root, naming fldtk.lib and the system libraries it needs:

    dmd -Isource example.d fldtk.lib gdi32.lib user32.lib kernel32.lib msvcrt120.lib oldnames.lib ole32.lib gdiplus.lib opengl32.lib glu32.lib msimg32.lib shell32.lib comdlg32.lib imm32.lib

The whole list is needed even for a program that draws no GL and
prints nothing: the static library brings its GL, GDI+, printing and
COM code with it. And once any .lib is named explicitly, dmd stops
adding its default runtime libraries (kernel32, msvcrt120, oldnames)
on its own, so those have to be listed too. buildsamples.d uses exactly
this list.


## Cairo and Pango on Windows

This has been tested on Windows: the Cairo demos (`cairo_test`,
`cairo_draw_x`) run, and so does a program laying out text with Pango.
Which scripts and emoji Pango can show depends on the fonts installed on
the machine.

Windows has no Cairo or Pango, so a Windows build leaves them out unless
asked. With them, fldtk links Cairo, Pango and everything they depend on
statically into each program: the result is a single .exe that needs
nothing installed (no GTK runtime, no DLLs), and can be copied to any
Windows 10 or 11 machine as it is.

The libraries are built once, from source, with
[MSYS2](https://www.msys2.org)'s UCRT64 toolchain (GCC and meson), and
their static archives (`lib*.a`), together with those of their
dependencies and of the MinGW/GCC runtime, are copied into the
repository's `libraries` folder. dub.sdl's `windows-cairo` configuration links them from
there. No Visual Studio is needed: UCRT64's GCC compiles against the
Universal C runtime (`ucrtbase.dll`, part of Windows 10 and 11), and dmd
links the same runtime with its own bundled import libraries, so each
program has one C runtime.

Everything other than Cairo and Pango (GLib, HarfBuzz, FreeType,
pixman, libpng, fribidi, ...) comes from MSYS2's packages, which ship
static libraries alongside the DLLs.

### Building the libraries

The `libpango-1.0.a`, `libpangocairo-1.0.a` and `libpangowin32-1.0.a`
archives in `libraries` have to be built with GLib's
static-build defines. Without them, Pango calls GLib through DLL-style
`__imp_g_...` references. dmd's bundled lld-link (9.0.0) resolves those
against the static GLib in a single pass only, so a program that uses
enough of Pango fails to link with undefined
`__imp_g_unichar_break_type`, `__imp_g_io_error_quark` and
`__imp_g_list_model_*`.

Steps 1-5 produce all the static libraries needed for a cairo/pango build on windows using MSYS2.
Run everything in the **MSYS2 UCRT64** shell (`ucrt64.exe`), not MINGW64 or MSYS.

#### 1. Tools and dependencies

Skip any package that's already installed (`--needed` does that).

    pacman -Syu
    pacman -S --needed git mingw-w64-ucrt-x86_64-gcc mingw-w64-ucrt-x86_64-meson mingw-w64-ucrt-x86_64-ninja mingw-w64-ucrt-x86_64-pkgconf \
        mingw-w64-ucrt-x86_64-glib2 mingw-w64-ucrt-x86_64-harfbuzz mingw-w64-ucrt-x86_64-fribidi mingw-w64-ucrt-x86_64-pixman \
        mingw-w64-ucrt-x86_64-libpng

Check that the UCRT64 tools are the ones found:

    which gcc meson pkg-config       # all three should be under /ucrt64/bin

#### 2. Sources

Skip a clone if that directory already exists. The following steps assume you are running this in your home folder.
fldtk tested correctly with the example versions of the libraries shown in the following steps; other versions may work too:

    git clone --depth 1 --branch 1.18.4 https://gitlab.freedesktop.org/cairo/cairo.git cairo-1.18.4
    git clone --depth 1 --branch 1.57.1 https://gitlab.gnome.org/GNOME/pango.git pango-1.57.1

#### 3. Cairo

    cd cairo-1.18.4
    meson setup staticminimal --default-library=static --buildtype=release \
        -Ddwrite=disabled -Dfontconfig=disabled -Dfreetype=disabled -Dglib=disabled -Dlzo=disabled \
        -Dspectre=disabled -Dsymbol-lookup=disabled -Dtee=disabled -Dtests=disabled
    meson compile -C staticminimal
    meson install -C staticminimal

`meson setup`'s summary should list Win32 surface: YES, Win32 font: YES, Win32 DWrite: NO.

#### 4. Pango

    pkg-config --modversion cairo        # must print 1.18.4

    cd ../pango-1.57.1
    STATIC_DEFS="-DGLIB_STATIC_COMPILATION -DGOBJECT_STATIC_COMPILATION -DGIO_STATIC_COMPILATION -DGMODULE_STATIC_COMPILATION -DCAIRO_WIN32_STATIC_BUILD"
    meson setup staticminimal --default-library=static --buildtype=release --wrap-mode=nofallback \
        -Dfontconfig=disabled -Dfreetype=disabled -Dxft=disabled -Dlibthai=disabled -Dintrospection=disabled \
        -Dbuild-examples=false -Dbuild-testsuite=false \
        -Dc_args="$STATIC_DEFS" -Dcpp_args="$STATIC_DEFS"
    meson compile -C staticminimal
    meson install -C staticminimal

**Check before copying anything.** Each line must end in `: 0`:

    for f in staticminimal/pango/lib*.a; do echo "$f: $(nm $f | grep -c ' U __imp_g_')"; done

If any count is not 0, the defines didn't reach the compiler. Look at
`meson configure staticminimal | grep _args` to see whether `c_args` and `cpp_args` carry them.

#### 5. Collect the archives

All 28 archives come from the same machine, so Cairo, Pango and their
dependencies match. Copy them into a folder to carry home:

    cd ~/fldtk
    cp ~/pango-1.57.1/staticminimal/pango/lib*.a .
    cp ~/cairo-1.18.4/staticminimal/src/libcairo.a .
    cp /ucrt64/lib/gcc/x86_64-w64-mingw32/*/libgcc.a /ucrt64/lib/gcc/x86_64-w64-mingw32/*/libgcc_eh.a .
    cd /ucrt64/lib
    cp libgio-2.0.a libgobject-2.0.a libgmodule-2.0.a libglib-2.0.a libintl.a libiconv.a libffi.a libfribidi.a libharfbuzz.a \
       libfreetype.a libbz2.a libbrotlidec.a libbrotlicommon.a libpcre2-8.a libgraphite2.a libpng16.a libpixman-1.a \
       libstdc++.a libmingwex.a libwinpthread.a libucrt.a libuuid.a ~/fldtk

#### 6. Back on the home machine

The archives are not part of the repository: some of them are under
licenses incompatible with fldtk's own (see "Licenses" below), so
`libraries/` is gitignored. On a fresh checkout, create the folder first, from the
repository root:

    mkdir libraries

Copy the 28 files into it. Then, from the repository root:

    rdmd buildsamples.d --cairo

should build all the example and test programs including the cairo test programs.

### Notes on the steps

*Step 1.* `pacman -Syu` may ask you to close the shell and run it again.
The packages also pull in FreeType, graphite2, brotli, bzip2, PCRE2,
libffi, gettext's libintl and libiconv, which all end up linked too.
Leave `PKG_CONFIG_PATH` as the shell sets it
(`/ucrt64/lib/pkgconfig:/ucrt64/share/pkgconfig`): `meson install`
puts both libraries into `/ucrt64` (meson's default prefix in the UCRT64
shell), where pkg-config looks anyway. See "Troubleshooting" below if
it has been changed.

*Step 3.* The sources are the releases fldtk's bindings were transcribed
from: Cairo 1.18.4 (`fl.cairo_c`) and Pango 1.57.1 (`fl.pango_c`).
What Cairo's options leave out, and why:

- `dwrite`: the DirectWrite font backend, which is C++ and which fldtk's
  bindings don't cover. Text goes through Cairo's GDI font backend.
- `fontconfig`, `freetype`: font backends that, on Windows, need a
  fonts.conf at run time.
- `glib` (cairo-gobject), `lzo`, `spectre`, `symbol-lookup`, `tee`:
  extras nothing in fldtk uses.
- `tests`: Cairo's test suite. Built without this option, it runs from
  the source tree's `test` directory with
  `srcdir=. ../staticminimal/test/cairo-test-suite`. Expect failures for
  the `script` and `win32-window-*` targets and in text-heavy tests (the
  reference images come from Linux); the `image` and `win32` targets
  are the meaningful ones.

PNG support stays on: Cairo's PNG functions and its SVG surface need
libpng. (fldtk's own PNG code and SVG export don't use it.)

Cairo 1.18.4's installed `cairo.pc` doesn't record that the library is
static. Without `-DCAIRO_WIN32_STATIC_BUILD`, `cairo.h` declares every
function `__declspec(dllimport)`, and code compiled against it (Pango,
next) expects a Cairo DLL. Step 4 therefore passes the define to Pango's
compiler.

*Step 4.* Pango is compiled with GLib's static-build defines for the
same reason: MSYS2's GLib `.pc` files don't carry them, and without
them every GLib call in Pango goes through a DLL import.

- `--wrap-mode=nofallback` makes meson stop with an error when a
  dependency isn't found, instead of quietly downloading and building
  its own copy (Pango ships fallbacks for Cairo, GLib and HarfBuzz).
- Pango's Windows font backend (pangowin32, DirectWrite) is always
  built on Windows and is C++, so programs link libstdc++.
- The build also links Pango's utilities (pango-view and others) against
  the static Cairo, which makes it a first check: they only link when
  Cairo's define reached Pango.

*Step 5.* The archives are about 30 MB, gitignored. The first group is
Cairo, Pango and their dependencies. The rest (`libstdc++` onwards, plus
`libgcc` and `libgcc_eh`) is the part of the MinGW/GCC runtime their
code calls beyond the C runtime: C++ support (`libstdc++`,
`libgcc_eh`), compiler helpers (`libgcc`), MinGW's
implementations of C functions the Universal C runtime doesn't export
(`libmingwex`, `libucrt`), threads (`libwinpthread`) and GUID constants
(`libuuid`). `libz.a` is not among them: Phobos already contains zlib.
Neither are `libssp.a` (in UCRT64 an empty archive, since the stack
protector lives in `libmingwex`) or `libatomic.a` (none of the other
archives calls it). dub.sdl's `windows-cairo`
lflags list exactly these files; a program that fails to link names the
missing or stale one.

*Step 6.* `rdmd buildsamples.d --cairo` does the same in any shell;
`dub build --config=windows-cairo` builds only the library, and
`rdmd buildsamples.d --cairo test cairo_test` a single demo. The
library is fldtk-cairo.lib, separate from the plain fldtk.lib, which
stays as it is: a static library with Cairo support pulls Cairo into
every program linked against it, so Fluid and programs without Cairo
keep using fldtk.lib.

### How the link works

dmd's library tool can't merge GCC-built
objects into fldtk-cairo.lib, so the archives are linked next to it.
The `windows-cairo` configuration's `libs` and `lflags` hold the whole
link line, and dub passes them on to every program that depends on
fldtk; buildsamples.d reads the same
list with `dub describe`, so dub.sdl is the only place it is written
down. It differs from the plain Windows build in a few ways, each
explained in dub.sdl's comment on the configuration:

- the Universal C runtime (`-mscrtlib=vcruntime140`, `vcruntime140.lib`,
  `ucrtbase.lib`, `legacy_stdio_definitions.lib`) instead of msvcrt120;
- lld-link runs in its MinGW mode (`-lldmingw`), which GCC's C++
  sections in HarfBuzz and Pango need;
- `phobos64.lib` is named ahead of all the MinGW runtime archives,
  because `libgcc.a` defines its own `__alloca` (with a calling
  convention dmd's code doesn't expect) and `libucrt.a` defines
  `__local_stdio_printf_options`, and Phobos's copy of each has to win;
- `/IMPLIB:NUL` discards the import library (`<program>.lib`) lld-link
  would otherwise write next to every program: MSYS2's static pixman
  still marks its functions for export from a DLL, so each program
  exports them. lld-link can't actually write to `NUL` (it writes through
  a temporary file it renames into place, which fails with "permission
  denied"), so `buildsamples.d` replaces it with
  `/IMPLIB:build/obj/<program>.lib`; a program of your own linking
  against this configuration needs the same substitution.

Several of the libraries (pixman, GLib, GObject, libstdc++) initialize
themselves in GCC constructor functions, which MinGW's own start-up
code would call but the C runtime start-up a D program uses doesn't.
fldtk's `fl.mingw_runtime` module calls them before any fldtk code
runs; nothing needs doing for that in a program.

### Building your own program

A dub project selects
`subConfiguration "fldtk" "windows-cairo"`, which brings the versions,
the C runtime flag and the whole link line. On the command line, from
the repository root (in an MSYS2 or Git Bash shell, so `$(...)` works),
compile with both versions and the UCRT flag and add the configuration's
link line; name fldtk-cairo.lib with a path, since lld-link in MinGW mode
doesn't search the current directory for it:

    dmd -Isource -version=FLDTK_HAVE_CAIRO -version=FLDTK_HAVE_PANGO -mscrtlib=vcruntime140 \
        example.d ./fldtk-cairo.lib \
        $(dub describe --config=windows-cairo --data=libs --data-list | tr -d '\015' | sed 's/$/.lib/') \
        $(dub describe --config=windows-cairo --data=lflags --data-list | tr -d '\015' | tr '\134' / | sed 's/^/-L/')

(dub ends its lines with CRLF; `tr -d '\015'` strips the carriage
returns, which would otherwise end up inside every library name.)

### Troubleshooting

A build directory keeps the dependencies and flags
it was first configured with, including which Cairo it found, so after
fixing any of the following, delete it (`rm -rf staticminimal`) before
rerunning that step's `meson setup`.

- *Pango's `meson setup` stops with "Dependency 'cairo' is required but
  not found", or Pango's build links a Cairo from somewhere else.*
  `pkg-config --variable=prefix cairo` shows which `cairo.pc` is found;
  it should be `C:/msys64/ucrt64`. The usual cause is a changed
  `PKG_CONFIG_PATH`. Reset it with
  `export PKG_CONFIG_PATH=/ucrt64/lib/pkgconfig:/ucrt64/share/pkgconfig`
  (or open a new UCRT64 shell, and check `~/.bashrc` doesn't set it),
  then rerun step 4. Entries in it must be in
  MSYS2 form (`/c/...`, never `C:/...`): the shell converts the list to
  Windows form for native programs like pkg-config, but leaves a value
  that already starts with `C:` as it is, and pkg-config then reads the
  whole `:`-separated list as one nonexistent directory.
- *Undefined `__imp_cairo_...` symbols while Pango links its utilities.*
  Pango was compiled without `-DCAIRO_WIN32_STATIC_BUILD`: it is missing
  from step 4's `STATIC_DEFS`, or the build directory was configured
  before it was added. Check with `meson configure staticminimal | grep
  _args`, then rerun step 4.
- *Undefined `__imp_g_...` symbols when linking a D program that uses
  Pango.* Pango was built without step 4's GLib defines; the `nm` check
  in step 4 shows it. Rerun step 4 and copy its three
  archives again (step 5).

### Updating or removing the libraries

After `pacman -Syu` upgrades
any of the packages in step 1, repeat step 5 so the copies in the
repository match; Cairo and Pango need rebuilding only for a new GCC
(delete both `staticminimal` directories, then rerun steps 3 to 5). pacman doesn't know about the
self-built Cairo and Pango in `/ucrt64`: if something ever pulls in
pacman's own `mingw-w64-ucrt-x86_64-cairo` or `-pango`, it refuses with
"exists in filesystem" errors. `ninja -C staticminimal uninstall` in
each source directory removes the self-built files first.

### Licenses

Cairo is available under the LGPL 2.1 or the MPL 1.1;
Pango, GLib and fribidi are LGPL 2.1 (the other dependencies use
permissive licenses). Linking an LGPL library statically into a program
you distribute obliges you to let its users relink the program against
a modified version of that library, typically by providing the
program's object files. That is no burden for open-source programs; for
closed-source ones, check what it means for you.


## Release builds: not currently supported

**Only the plain `dub build` (debug) library is supported right now.
Don't ship or rely on an optimized build of fldtk/Fluid.** This isn't
a gap in this project's own code -- it's real, currently-open bugs in
both D compilers available to build it, discovered while investigating
whether a release build was even possible:

- **DMD 2.112.0-2.113.0 crash outright** compiling `source/fl/platform_x11.d`
  with `-O` or `-inline` (either alone is enough; `-release` alone is
  fine) -- an internal compiler error. A bug report was filed and was fixed
  by the dmd team, but will not be available until a future release.
- **GDC 14.2.0 can build the library itself** (`dub build
  --compiler=gdc --build=release` produces a real, loadable
  `libfldtk.so`), but hits its own internal compiler error building
  Fluid, unrelated to the DMD one (a large map literal in
  `source/fluid/code_writer.d` trips GCC's D-frontend bounds-check
  codegen under `-frelease` specifically).
- **Working around the DMD crash doesn't produce something usable
  either.** Compiling `platform_x11.d` separately with `-release`
  only (skipping `-O`/`-inline` just for that one file, everything
  else fully optimized) does sidestep the crash and link into a real
  `libfldtk.so` -- but running real sample programs against it turned
  up serious, silent problems that don't exist in the debug build:
  `fractals` showed no meaningful speedup, window repaint after being
  obscured/re-exposed lagged noticeably, GL windows had real painting
  glitches, text rendering broke in places (only the upper half of
  glyphs drew), some ordinary widgets had their own drawing problems,
  and several example programs segfaulted outright. None of that is
  from the one known ICE (which was worked around) -- it's DMD's
  `-O`/`-inline` optimizer silently miscompiling other, unrelated code
  elsewhere in `source/fl/`, not yet bisected to a specific file.
  A build that produces wrong pixels or crashes without warning is
  worse than one that fails to compile at all.

To try a release build without replacing the debug libfldtk.so (which
Fluid and the samples are linked against), use the
separate `linux-release` configuration:

    dub build --config=linux-release --build=release                  # dmd
    dub build --config=linux-release --build=release --compiler=gdc   # gdc

It writes build/release/libfldtk-release.so. Any dub build type works
(`release-nobounds`, `plain`, ...). With DMD 2.112.0 this still dies
with the crash described above (the compiler exits with SIGILL); GDC
15.2.0 builds the library successfully.

To exercise the GDC release library with real programs, without
touching the debug build:

    rdmd buildsamples.d --release              # everything
    rdmd buildsamples.d --release test hello   # one program, as usual

This builds the library the same way as above (`--config=linux-release
--build=release --compiler=gdc`) if it's stale, then compiles every
sample with `gdc` instead of `dmd` and links against
build/release/libfldtk-release.so, writing binaries to build/release/
instead of build/ so they never collide with the debug ones. Every
buildable sample links cleanly this way (the same handful of programs
`buildsamples.d`'s own `skip`/`skipWindows` tables list stay skipped,
for the same reasons), and every one of them has been run and behaves
identically to its plain dmd debug build. GDC is a viable alternative
compiler for building fldtk, not just a way to test around DMD's own
`-O`/`-inline` crash -- worth keeping regardless of whether DMD's
optimizer ever gets fixed, since it widens which toolchains fldtk can be
built with.

**If you have a local, not-yet-released DMD fix for the crash above**
(e.g. a compiler patch accepted FLTK but not in any tagged DMD
release yet): building the one file that fails to compile as
unoptimized/no-bounds-checks and linking it into an otherwise-optimized
library is a normal, standard workaround -- neither dub.sdl's
configurations nor `buildsamples.d --release` do this automatically,
since it depends on which file and which DMD build you're working
around. Roughly:

    mkdir -p build/release/objs
    dmd -c -release -Isource -odbuild/release/objs source/fl/platform_x11.d      # no -O/-inline: sidesteps the crash
    dmd -c -release -O -inline -Isource -odbuild/release/objs $(other source/fl/*.d)
    dmd -shared -of=build/release/libfldtk-release.so build/release/objs/*.o -L-lX11 -L-lXft -L-lXinerama -L-lfontconfig -L-lXcursor -L-lXfixes -L-lXext -L-lXi -L-lGL -L-lGLU -L-lz

adjusting for whichever file/flag combination the fix you have actually
needs.

Given all of that, **the project's own stance for now is: build and
ship debug only**, until DMD's optimizer is fixed enough to trust. If
you're reading this later and DMD has released a fix, it's worth
re-testing this whole section from scratch rather than assuming
anything above still holds.
